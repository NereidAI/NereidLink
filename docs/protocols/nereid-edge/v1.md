# NereidEdge Integration Protocol v1

- Status: Draft v1 (2026-09-26)
- Basis: ADR-0026, ADR-0026

## 1. Overview

Communication protocol between NereidEdge (NE) and NereidLink (NL).

| Item | Specification |
|---|---|
| Baseline transport | MQTT 3.1.1 / 5.0 over TLS (mTLS optional) |
| Enhanced transport | NATS leafnode (Go Edge only, optional) |
| Data plane | HTTPS relay endpoints (blobs/firmware) |
| Authentication | Connector credentials: username/password or X.509 client cert |
| Message format | JSON (Envelope JSON encoding), UTF-8 |
| Session | hello negotiation handshake; version/features bound per session |

### 1.1 Communication Model (One Sentence and Three Steps)

The entire protocol can be summarized as: **hello declares "who I am, what I understand, and which functions we negotiate"; afterward,
both sides exchange messages by topic over one connection—NL handles binding/orchestration/risk control, while Edge only executes local protocols and reports back; secrets and object storage remain opaque to Edge.**

1. **Upstream declaration (Edge → NL, hello).** Edge advertises a **type catalog (schemas), not instances**, in four categories
   (see §3 for details):
   - `connectors` — supported connector types and their configuration JSON Schemas (for example, modbus);
   - `secret_types` — credential-type schemas (for example, onvif-basic), determining which credentials NL may deliver to the gateway;
   - `operations` — whole-gateway operation descriptors (interaction mode, timeout, risk level, parameter/result schemas);
   - `features` — required/optional capability switches (telemetry/presence/ota/shadow/blob-relay/
     command/secrets). Failure to satisfy required capabilities fails the handshake; optional capabilities are degraded to their intersection.
   The platform compiles and persists these schemas; an invalid individual schema is reported per item in the Ack and does not fail the entire session.
2. **NL assembly/orchestration.** The control plane combines "gateway — subdevice (`owning_gateway` binding) — connector instance —
   profile/protocol — credentials" and performs validation, risk control, and quota enforcement. The platform itself contains no business logic or built-in protocol/
   operation names; all semantics come from tenant definitions and descriptors advertised by Edge.
3. **Downstream delivery (NL → Edge) + upstream reporting.** The assembled results are dispatched by topic over the same connection (command,
   ota/task, probe, connectors/spec, secrets/sync, operations/invoke, attributes/push,
   discovery/result, etc.); after executing local protocols, Edge reports responses/progress/status on the corresponding topics. See
   §4 for the complete direction matrix.

**Ownership boundary (applies throughout):** each subdevice is bound to exactly one gateway through `owning_gateway`, and a gateway receives only
downstream frames for its own devices; secret delivery, connector specs, and media blobs are isolated by tenant/gateway/device scope, and Edge can never obtain
credentials for the NL vault or object storage.

## 2. Versions and Compatibility

- The bootstrap message `v1/gateway/hello` is a permanently stable endpoint; only optional fields may be added. It carries `v` (hello format version).
- The supported protocol version range is declared in hello through `proto.min/max` (major.minor).
- Version selection: choose the highest version in the intersection; reject incompatible majors and return the server range.
- Compatibility depth (N-k) is an NL-side policy setting.
- The Edge agent version is an independent field and is not conflated with the protocol version.

## 3. Connection and Handshake

Connection state machine: `UNIDENTIFIED → NEGOTIATED → CLOSED`.

1. Establish MQTT + TLS; pre-register the LWT for `v1/gateway/goodbye`.
2. Subscribe to hello responses (or use the MQTT5 ResponseTopic).
3. Publish `v1/gateway/hello`; disconnect if negotiation does not complete within 10s by default.
4. Data topics may be used only after successful negotiation; negotiate exactly once per connection.

### Hello（Edge → NL），topic `v1/gateway/hello`

```json
{
  "v": 1,
  "edge_id": "edge-001",
  "agent_version": "2.3.1",
  "proto": {"min": "1.0", "max": "1.4"},
  "features": {
    "required": ["telemetry", "presence"],
    "optional": ["ota", "shadow", "blob-relay", "command"]
  },
  "connectors": [
    {"type": "modbus", "type_version": "2.1",
     "config_schema": {"$schema":"https://json-schema.org/draft/2020-12/schema",
                        "type":"object","required":["host"],
                        "properties":{"host":{"type":"string"},"port":{"type":"integer"}}}},
    {"type": "onvif", "type_version": "1.0", "config_schema": { }},
    {"type": "mqtt-remote", "type_version": "1.2", "config_schema": { }}
  ],
  "secret_types": [
    {"type": "onvif-basic", "type_version": "1.0",
     "fields_schema": {"$schema":"https://json-schema.org/draft/2020-12/schema",
                       "type":"object","required":["username","password"],
                       "properties":{"username":{"type":"string"},
                                     "password":{"type":"string","format":"password"}}},
     "display_name": {"en": "ONVIF credentials", "zh": "ONVIF 凭据"}}
  ],
  "operations": [
    {"operation": "reboot", "type_version": "1.0",
     "display_name": {"en": "Reboot", "zh": "重启"},
     "interaction": "request-response", "timeout_ms": 15000,
     "risk": "dangerous",
     "param_schema": {"$schema":"https://json-schema.org/draft/2020-12/schema",
                      "type":"object"},
     "result_schema": {"$schema":"https://json-schema.org/draft/2020-12/schema",
                       "type":"object"}}
  ],
  "resume": {"session_id": "s_abc", "last_cursor": {"telemetry": 12345}},
  "caps": {"max_upload_mb": 256},
  "client_time": 1727360000123
}
```

> Hello/Ack may also carry an optional `inference` block to negotiate edge model inference capabilities (ADR-0039); see [§15](#15-edge-model-inferenceadr-0039). Without negotiation, the edge sends no `models` section and receives no `edge-inference` spec, behaving exactly like old firmware.

### Ack（NL → Edge）

```json
{
  "session_id": "s_new",
  "status": "ok",
  "selected": "1.4",
  "server": {"min": "1.0", "max": "2.0", "version": "nereidlink-1.5.0"},
  "features": ["telemetry", "presence", "ota", "shadow", "blob-relay", "command"],
  "limits": {"heartbeat_s": 30, "hello_timeout_s": 10,
             "upload": {"max_mb": 256, "qps": 20}},
  "time": {"server_time": 1727360000456, "offset_ms": -312, "clock_warning": false},
  "resume": {"accepted": true, "replay_from": 12000},
  "connector_schemas": [
    {"type": "modbus", "type_version": "2.1", "accepted": true},
    {"type": "onvif", "type_version": "1.0", "accepted": false,
     "reason": "invalid schema: ..."}
  ],
  "secret_types": [
    {"type": "onvif-basic", "type_version": "1.0", "accepted": true}
  ],
  "operations": [
    {"operation": "reboot", "type_version": "1.0", "accepted": true}
  ]
}
```

Status: `ok / auth_failed / incompatible_version / incompatible_features / quota_exceeded`; clock skew sets a warning flag and does not cause rejection.

`connectors[]` is optional; each element carries the edge's self-described, **self-contained inline** configuration JSON Schema (external `$ref` / schema URLs are not supported).
The platform compiles and registers schemas by `(type, type_version)` during hello; reconnects/retransmissions perform an upsert (replacing the old document).
An invalid individual schema does not affect the handshake: the handshake status may still be `ok`, with per-item results returned in ack `connector_schemas[]`;
when `accepted=false`, a `reason` is supplied. The platform is **fail-open for connector types with no registered schema** (allows them),
while registered types have their configuration validated against the schema when creating/updating a connector spec (including its referenced profile template and instance override); violations return HTTP 400.
The template configuration and instance override each pass schema validation independently (an instance override is not a complete configuration).

Each `connectors[]` element may optionally carry `protocol` (an open string protocol family, such as `modbus`) and
`transports[]` (specific transport keys within the family, such as `modbus-tcp/modbus-rtu`). When creating a connector spec, the platform uses these to
validate that its protocol family matches the referenced profile; if either side does not declare one, validation is fail-open (see the profile section in §7).

`secret_types[]` is optional; each element describes an edge credential type supported by the gateway: a self-contained, **inline**
draft 2020-12 `fields_schema` (external `$ref` is not supported), optional `type_version`, and bilingual `display_name`.
During hello, the platform compiles and registers these in the **tenant-scoped** secret-type catalog (table `edge_secret_type`, migration 0067);
reconnect retransmission is an upsert. Descriptors advertised by a gateway are read-only to users (they may be cloned as manual types). An invalid individual schema does not affect the handshake;
per-item results are returned in ack `secret_types[]`, with `reason` when `accepted=false`. The platform is fail-open for unregistered credential types
(free-form key-value pairs); for registered types, it validates the credential document against the schema when writing the secret.

`operations[]` is **optional, but when present it is the complete set of operations currently supported by that gateway**; each element is a
whole-gateway operation descriptor supported by the gateway (ADR-0035): `operation`, optional `type_version`, `interaction`
(request-response/one-way), `timeout_ms` (100..60000, default 15000), `risk`
(read/normal/dangerous, default normal), self-contained **inline** parameter/result schemas (draft 2020-12,
no external `$ref`/URL), and a bilingual display name. The platform has no built-in operation names, and risk levels come only from descriptors; operations
are a gateway capability and **do not need** to be declared in hello `features`.

Descriptors are **stored separately for each advertising gateway** (table `gateway_operation_advertisement`, primary key
`(gateway_id, operation, type_version)`, migration 0080). Therefore:

- **Full reconciliation**: every hello replaces the full set for that gateway—an existing `(operation,type_version)` omitted from the current hello
  is deleted. An omitted field (old firmware does not send `operations`; it decodes as null) means "no statement", and the platform retains the existing set;
  only an explicit `[]` means the gateway currently supports no operations and clears the set.
- **Same-name isolation**: two gateways advertising the same `operation`+`type_version` do not overwrite each other; when invoking a gateway, its parameter
  schema, risk, and timeout always come from **the target gateway's own copy**. A tenant-private descriptor (table `tenant_operation`)
  is used as a fallback only when the target gateway has not advertised that operation.
- **Latest of multiple versions**: when one gateway advertises multiple `type_version` values for the same `operation`, invocation (whose frame carries no
  version) selects one by latest `updated_at`, then `type_version` order; a normal implementation advertises only one current version per operation.
- An invalid individual schema does not affect the handshake: entries are compiled and validated independently, with results returned in ack `operations[]`
  (`accepted/reason`); rejected entries are not persisted.

**Naming and version contract** (convention for multi-vendor coexistence):

- `operation`+`type_version` is the contract: across gateways, the same name and version MUST have identical parameters, results, risk, and interaction.
- Generic operations use the standard namespaces `diag.*` (diagnostics), `sys.*` (local information/maintenance), and `service.*` (managed services);
  vendor-specific operations MUST use `vendor.<vendor-id>.*` to avoid collisions with standard keys.
- A breaking change (parameters/results/risk) MUST use a new `type_version` or a new `operation` key (for example,
  `diag.ping.v2`); changing the semantics of the same name and version in place is forbidden.
- The console catalog is an **aggregated view** of gateway advertisements: it merges by `(operation,type_version)` and lists the
  gateways advertising each key; inconsistent contracts with the same name/version are marked as conflicts, prompting firmware alignment or different keys. Users can clone an edge descriptor
  as tenant-private or disable a key per tenant.

Session recovery (`resume`): on reconnect, Edge may include the previous session in hello as
`{"session_id": "s_...", "last_cursor": {...}}`. A session is **in-process node-local state**; only when
Edge reconnects to the same node with the same tenant and `edge_id`, within the session TTL (default 24h), does the platform return
`resume.accepted=true` and reuse the original `session_id`; an unknown/expired id or identity mismatch returns
`accepted=false` and issues a completely new session (recovery is an optimization, never a handshake prerequisite). Downstream desired is
full declarative state, and the complete connector set is idempotently retransmitted after every handshake, so `last_cursor` is accepted only for forward
compatibility and no cursor-based incremental replay is currently performed (`ack.resume` does not return `replay_from`).

### 4.1 On-Demand Attribute Pull and Deletion

Platform attributes `SERVER_SCOPE`/`SHARED_SCOPE` remain consistent through incremental push + pull-on-online; `CLIENT` is device-owned, and the platform neither pushes it back nor accepts pulls for it.

> Scope visibility: in the current implementation, both `SERVER_SCOPE` and `SHARED_SCOPE` **are delivered to devices** (both online push and offline get compensation include both). This differs from classic ThingsBoard semantics, where `SERVER_SCOPE` is platform-private and only `SHARED_SCOPE` is device-visible. Edge firmware MUST NOT assume `SERVER_SCOPE` is private; new platform-side configuration intended for device consumption SHOULD consistently use `SHARED_SCOPE`.

- **Incremental downstream**: the gateway itself receives `v1/me/attributes/down`, and subdevices receive `v1/gateway/attributes/push` (the frame carries `device`).
  Frame `{"scope":"SHARED_SCOPE","data":{"k":<json>}}` contains only changed keys. `data[k]` set to JSON `null` means the key has been deleted on the platform, and the edge MUST remove it from its local cache (it MUST NOT cache null).
- **On-demand pull**: after each (re)hello, the gateway PUBLISHes `v1/me/attributes/get` for itself and PUBLISHes `v1/gateway/attributes/get` for each subdevice attached to the current connection (the frame carries `device`).
  Request `{"scopes":[...],"response_topic?"}`; omitted/empty `scopes` means both platform scopes. Explicitly requesting `CLIENT` or an unknown scope is rejected. Responses arrive at `.../get/ack` as `{"scopes":{"SERVER_SCOPE":{...},"SHARED_SCOPE":{...}}}` (gateway-proxy frames additionally carry `device`); each scope is the current full key-value set, and the edge replaces its entire cache for that scope.
- Pulls for unattached subdevices are discarded; QoS1, all frames idempotent, retransmission allowed.

### 4.2 Device Shadow

A Shadow is a per-device platform-side copy of "desired state + actual state" used to confirm "whether the device has reached the state I requested". It is stored by device UUID and is transport-independent: direct devices and the gateway itself use `v1/me/shadow/*`, while gateway-**proxied subdevices** use `v1/gateway/shadow/*`.

Boundary with adjacent mechanisms: use commands (command/operation) for one-shot actions and attributes (SHARED attributes) for one-way configuration whose application is not tracked; **use shadow only for state that must be maintained toward a target and confirmed as eventually reached by the device.**

**Logical Model (stored by the platform, one per device)**

```json
{
  "device_id": "uuid",
  "desired":  {"mode":"AUTO","recording":true},
  "reported": {"mode":"AUTO","recording":false},
  "delta":    {"recording":true},
  "desired_version": 7,
  "reported_version": 6,
  "etag": "\"7\"",
  "in_sync": false
}
```

- The platform writes `desired`, and the device writes `reported`; both are top-level key maps. The platform computes `delta` from keys "missing from or unequal in reported relative to desired"; empty `delta` means `in_sync=true`.
- `desired_version` increments only when desired **content actually changes** (idempotent retransmission of identical content does not increment it). The device includes the version it has applied when reporting, which the platform records as `reported_version`; if omitted, it is aligned with the current desired_version.
- State values may be arbitrary JSON (scalar/object/array), not only scalars.

**Convergence loop**: platform writes desired (merge; version++ if content changes) → immediately push when online, and replay the **full** state when device presence transitions to ONLINE while offline → device replaces its entire local desired, deduplicates by version, and applies on a best-effort basis → reports actual reported + applied version → platform merges and recomputes delta/in_sync. Devices need not actively get; shadow has no get topic.

**Direct Device / Gateway Itself (`v1/me`)**

| Direction | topic | Payload |
|---|---|---|
| Device→Platform | `v1/me/shadow/report` | `{"state":{...},"version":7?}` (reported patch) |
| Platform→Device | `v1/me/shadow/desired` (subscribe) | `{"version":7,"desired":{...}}` (**full**, no internal tenant/device fields) |

**Gateway-Proxied Subdevices (`v1/gateway`, batch arrays; one device means length 1)**

Upstream `v1/gateway/shadow/report`:
```json
{"reports":[
  {"device":"<uuid-a>","state":{"mode":"AUTO"},"version":7},
  {"device":"<uuid-b>","state":{"power":1}}
]}
```
Downstream `v1/gateway/shadow/desired` (the gateway subscribes once and dispatches to local subdevices by each entry's `device`):
```json
{"desired":[
  {"device":"<uuid-a>","version":7,"desired":{"mode":"AUTO","recording":true}},
  {"device":"<uuid-b>","version":3,"desired":{"power":1}}
]}
```

**Unified Semantics**

1. Downstream desired is **always full**; the device replaces the entire state, with no incremental update.
2. Upstream reported is a **patch**, merged by the platform at top-level keys.
3. **Key deletion**: a JSON `null` value for a key in a desired or report map deletes that top-level key (consistent with null deletion for attributes).
4. Desired frames are idempotently deduplicated by `version`; duplicate full frames and ONLINE replays are allowed.
5. A gateway may proxy only subdevices **attached** to the current connection.
6. QoS: downstream QoS0/non-retained; upstream publisher's choice (QoS1 recommended).

**Per-item isolation and auditing for batch frames**: if the top-level payload cannot be parsed as JSON, discard the entire frame; whenever `reports[]` can be parsed, authorize and persist each entry **independently**. If any entry has an empty/non-UUID `device`, a subdevice not attached to this gateway connection (unauthorized), or a non-object `state`, **discard only that entry** and merge the rest normally. The platform writes one audit record per rejection (CONFIG_CHANGE / device_shadow, including gateway, subdevice, and reason) and does not return per-item negative acknowledgments at the MQTT layer.

**Edge compatibility requirements (bar for third-party edges supporting the optional `shadow` feature)**: implement both me and gateway topic groups; full desired replacement + version deduplication; report actual reported state and applied version after application; converge through full ONLINE replay after reconnect/re-attach without relying on locally persisted cloud state; correctly handle `null` deletion; retain unknown keys in local desired without raising an error.

## 5. Link Health

NL has **two layers** of health signals, implemented separately and not conflated:

- **Transport layer**: MQTT keepalive (default 60s, declared dead after approximately 1.5 intervals without PINGRESP); on physical disconnection, presence immediately marks subdevices OFFLINE in batch (existing ADR-0010 behavior).
- **Application-layer watchdog** (this slice, `internal/linkhealth`): detects heartbeat loss even when TCP remains alive but the NE application is stuck.

### Heartbeat Frame (Edge → NL), topic `v1/gateway/heartbeat`

```json
{"seq": 123, "client_time": 1727360000123}
```

- The payload may be empty; an empty frame also renews the lease. Default cadence is 30s (communicated by hello ack `heartbeat_s`).
- NL records each gateway's last heartbeat time and evaluates it in a global sweep, with no per-gateway timer.

### State Machine and Thresholds (Configurable; Defaults Shown)

- One missed beat (silence ≥ `suspect_after`, default 45s): `HEALTHY → SUSPECT`, emit advisory.
- Three missed beats (silence ≥ `down_after`, default 90s): `SUSPECT → DOWN`, emit advisory; **even if transport remains online**, batch-transition presence for subdevices declared by this gateway to OFFLINE (reason `gateway_lease_expired`).
- Heartbeat recovery: SUSPECT silently returns to HEALTHY (no DOWN event); a heartbeat after DOWN emits `recovered`, and the next manifest/connect brings subdevices back ONLINE.

### Goodbye / LWT，topic `v1/gateway/goodbye`

```json
{"reason": "upgrade", "planned": true}
```

- Graceful shutdown sends `planned=true` (or reason `planned/shutdown/upgrade/restart/planned_down`): enter DOWN but mark `planned_down`, **without alarms or flapping count**.
- Physical disconnection is delivered by MQTT LWT on the same topic (`planned` omitted/false) or recognized as `transport_down` by the connection-close event; a close event immediately following goodbye is deduplicated and not counted twice.

### Flapping

- ≥5 **unplanned** DOWN cycles within a 10-minute sliding window → attach a `flapping` advisory to the 5th DOWN event (only once per burst; re-arm after the window slides out).
- Planned downtime does not count toward flapping.

### Advisory（NL → Core NATS）

- subject：`nl.linkhealth.<tenant>.<gateway>`。
- `kind`: `suspect` / `down` / `planned_down` / `recovered` / `flapping`; payload includes from/to, reason, and time.

### Alarms, Escalation, and Digests (NL Internal, `internal/linknotify`)

- `nl.linkhealth.*.*` is consumed by queue group `nl-linknotify` (processed only once across the cluster).
- An unplanned `down` (including flapping) opens a deduplicated `GATEWAY_LINK_DOWN` alarm (initially MAJOR, dedupe key is the gateway), reusing the existing ADR-0019 notification pipeline (in-app/webhook/SMTP with rate control); SUSPECT is observed without alarming; planned_down never alarms.
- `recovered` clears the alarm and closes the persisted downtime episode.
- An episode lasting longer than `escalation_after` (default 30m) is escalated once to CRITICAL; the claim occurs in the same UPDATE, so restarts/failovers escalate at most once (migration 0039 `gateway_link_episode`).
- Once per UTC calendar day at `digest_hour_utc` (default 08:00 UTC), send a 24h digest to tenant admins who **had an episode end on the previous day** (in-app + webhook/SMTP), aggregating count and total downtime by gateway; `gateway_link_digest` guarantees at most one per tenant per day.

### Local Watchdog Episode Backfill, topic `v1/gateway/linkhealth`

The Edge-local link watchdog opens an unplanned episode when the link breaks and closes it after a successful re-hello, making it the
**ground truth** for outage start/end; start/end inferred from the server-side lease (30s/90s heartbeat windows) are only estimates;
Edge actively backfills each episode after it closes:

```json
{
  "edge_id": "…gateway-device-UUID…",
  "session_id": "s_…",
  "down_at": "2026-10-10T03:12:44Z",
  "up_at":   "2026-10-10T03:12:49Z",
  "reason":   "transport_down",
  "response_topic": ""
}
```

- Send only after successful negotiation (QoS1). `edge_id` is required and must match the gateway device of the authenticated connection—the platform only validates it and
  never derives identity from the frame; `session_id` is optional (the platform session id from the last hello ack before the episode, for correlation only).
- `down_at`/`up_at` are required RFC3339 values (any timezone offset is accepted; the server normalizes to UTC), and `up_at` MUST NOT be earlier than
  `down_at`; `reason` is required, with documented value `transport_down`, and the platform will also accept future new values.
- Backfill backlog needs no protocol support: after restart, Edge simply sends ordinary QoS1 frames **oldest first**, and deduplication guarantees idempotency.

**Server Processing (migration 0075)**:

- **Correction**: if the time interval intersects a `lease` episode (2-minute tolerance covers the lease 90s detection delay) → update
  `started_at/ended_at` in place to edge ground truth, mark `source=edge`, and record `edge_down_at`; if the episode
  is still open, close it as well (retain the alarm, to be cleared normally by a subsequent recovered).
- **No match** (typically a seconds-long flap invisible to the lease 90s window) → directly insert a **closed, alarm-free**
  episode (`alarm_id` empty), without reopening old alarms or paging, but include it in the 24h digest.
- **Deduplication**: partial unique index `(gateway_id, edge_down_at)` records each outage only once; retransmitted/backlogged duplicate frames return
  `duplicate`.
- **Flapping**: backfills not matched to a lease enter an independent edge sliding window (same edge dimension, 10min ≥5, once per
  burst); crossing the threshold emits an edge-sourced `flapping` advisory and opens a `GATEWAY_LINK_FLAPPING` alarm; after the window has been quiet for a full
  10 minutes, emit `flap_settled` to automatically close the alarm and re-arm. Known limitation: long outages (lease-counted) and second-long outages
  (edge-counted) are tracked in separate windows, and mixed bursts are not counted across sources.

**Ack (NL → Edge)**: `v1/gateway/linkhealth/ack` (or in-frame `response_topic`):

```json
{"edge_id": "…", "down_at": "2026-10-10T03:12:44Z", "status": "accepted"}
```

- `accepted` = applied (correction or new insertion); `duplicate` = already exists, **stop retransmitting**; `rejected`
  (with reason) = validation failed, **stop retransmitting**. Unparseable frames are silently discarded; storage failures temporarily receive no ack,
  and Edge retries.

## 6. Manifest Reconciliation (5 Minutes)

- Edge triggers on **absolute wall-clock boundaries** (every 5:00/10:00…, configurable phase), aligning the timer to the boundary and waking slightly early.
- Contents: a full list of online subdevices plus running connector instances and config revisions carried in the heartbeat.
- Missed boundary: do not backfill the old beat; execute the current beat and report `missed_cycles` with the heartbeat.
- NL: reconcile immediately upon message arrival (event-driven); absence is triggered by the lease TTL watcher; a global sweep provides the fallback. No per-gateway timers.
- Reconciliation results: supplement ONLINE / transition to OFFLINE / desired-reported drift events.

### Manifest Frame (Edge → NL), topic `v1/gateway/manifest`

```json
{
  "devices": ["dev-a", "dev-b"],
  "connectors": [
    {"spec_id": "0c8e…", "revision": 3, "config_hash": "9f2a…"}
  ],
  "models": [
    {"id": "yiqisoft-yolov8n", "version": "1.0.0", "revision": "76937",
     "task": "detection", "family": "yolov8", "backend": "kserve",
     "model_name": "yolov8n", "state": "READY",
     "labels": ["person", "car"], "active_bindings": 1}
  ],
  "revision": 3,
  "missed_cycles": 0
}
```

- `devices` is **full** (not incremental): the list of currently online subdevice IDs. Every `devices` element must be a device already bound to this gateway through `gateway_id`; otherwise it is classified as `unregistered` and **will not** be automatically created or attached (autonomous provision is the sole exception and is not implemented in the current slice).
- `connectors` (optional) is the **full** list of connector instances currently **applied** by this gateway, with elements `{spec_id, revision, config_hash?}`:
  - `revision` = applied desired revision; `config_hash` is described below (if omitted, only existence/version reconciliation is performed, without detecting content tampering at the same revision).
  - An **omitted field** (old edge/unsupported) means the edge does not report the connector section; NL skips connector reconciliation and does not misclassify existing instances as missing. Explicit `"connectors": []` means zero current connectors, and all desired instances are recorded as `missing`.
- `models` (optional, ADR-0039) is the **full** list of this gateway's current local model inventory, with the same semantics as `connectors`: an omitted field (old edge/inference not negotiated) means no report, and NL leaves the inventory unchanged; explicit `"models": []` is an authoritative zero-inventory report that hard-deletes all inventory rows for the gateway. See [§15](#15-edge-model-inferenceadr-0039) for field definitions, the state machine, and reconciliation/alarm semantics.
- `revision`: desired version observed by Edge, used only for drift correlation and not enforced in this slice.
- `missed_cycles`: number of aligned boundaries skipped before this report.

**config_hash algorithm (both ends MUST match byte-for-byte)**: take sha256 of the effective configuration document, with input being compact, key-sorted
`{"config": <effective config object>, "mappings": <effective mappings array>}` JSON and output lowercase hex.
"Effective" means the same document applied by the edge after merging the profile template (identical to the spec downstream frame).

### Reconciliation Semantics (NL)

NL uses devices bound in the registry through `device.gateway_id` with status `ACTIVE`/`UNCLAIMED` as the **desired** set and in-frame `devices` as the **reported** set, divided into three classes:

| Classification | Condition | NL Action |
|---|---|---|
| `in_sync` | desired ∩ reported | Ensure presence ONLINE (idempotent with no event if already online) |
| `missing` | desired − reported | Transition presence declared by this gateway to OFFLINE (reason `manifest`); emit drift advisory |
| `unregistered` | reported − desired | Do not create presence or modify the registry; emit drift advisory |

- Default is **alarm-only**: drift never deletes a binding or creates a device; presence still converges according to reported.
- Write one audit-history row per cycle (including the three sets, promoted/derived counts, and drift flag).
- Lease: each received frame refreshes the gateway manifest lease (KV `gw-manifest`, TTL approximately 3 cycles). After the lease disappears (explicit deletion handled by watcher, silent TTL expiry covered by global sweep), batch-transition subdevices currently declared by that gateway to OFFLINE (reason `manifest_lease_expired`). Derive only once per expiry and re-arm after the gateway resumes reporting.

## 7. Connector Instance Lifecycle (desired / reported)

NL is the system of record for desired; Edge applies desired and reports reported. The core understands no connector protocol details: `config` / `mappings` are opaque JSON, and adding a connector type does not require an NL upgrade.

### Two-Level Configuration: Profile Template + Instance Override

Connector configuration has two levels (ADR-0026, migration 0042):

- **Profile stores the template/point table**: `device_profile` adds nullable connector-template fields
  `connector_type` / `connector_type_version` / `connector_config_template` (object)/
  `connector_mappings` (array). Empty `connector_type` means the profile contains only a telemetry point table (0005 semantics unchanged).
  Templates are managed through Profile CRUD (`profile:read/write`).
- **Instances store connection-parameter overrides**: `connector_instance` adds nullable `device_id` (bound to a subdevice under this gateway,
  at most one instance per subdevice) and `profile_id` (references a profile with a template). The instance's `config`/`mappings`
  are **per-device overrides**, not the full configuration.
- **Merge at dispatch** (`internal/connector/merge.go`):
  - `connector_type` / `type_version`: instance value takes precedence, inheriting the template when empty; if both are absent, return 400.
  - `config`: deep-merge objects, with instance values overriding same-named template keys and nested objects merged recursively by key; **arrays are replaced in full, never concatenated**.
  - `mappings`: a non-empty instance array replaces the entire template array; otherwise use the template.
- Persist overrides verbatim, and compute the merge from the current template **at push/redrive time**. Note that Edge deduplicates by
  `(spec_id, revision)`: editing only the profile template does not automatically increment the instance revision; to dispatch a template change,
  issue another PUT on the bound instance (triggering revision+1 and a repush); reconnect redrive remerges the current template at the same revision.
  When a profile is deleted, `profile_id` is set to null (`ON DELETE SET NULL`), and the instance retains its own overrides;
  deleting a subdevice cascades deletion of its connector configuration (`ON DELETE CASCADE`, non-business data).
- `device_id` must be a same-tenant, ACTIVE/UNCLAIMED subdevice bound to that gateway, otherwise return 400; creating a duplicate for the same subdevice
  returns 409. Gateway-level instances without `device_id` remain supported (legacy behavior).

### Desired spec（NL → Edge：`v1/gateway/connectors/spec`）

```json
{
  "kind": "spec",
  "tenant_id": "…uuid…",
  "gateway_id": "…uuid…",
  "spec_id": "…uuid…",
  "device_id": "…uuid, nullable…",
  "connector_type": "modbus-tcp",
  "type_version": "2.1",
  "config": {"host": "192.0.2.10", "unit_id": 1},
  "mappings": [{"register": "40001", "key": "voltage"}],
  "health_check": {
    "resource": "camera_status",
    "interval_ms": 30000,
    "timeout_ms": 5000,
    "fail_threshold": 3
  },
  "revision": 3
}
```

- Downstream `config`/`mappings` are the **effective merged values** of the template and instance overrides; `device_id` identifies the subdevice (nullable for gateway-level instances).
  Edge need not know that a template exists; it simply applies by `(spec_id, revision)`.

- `spec_id` is an NL-assigned UUID, echoed verbatim by Edge in status.
- `revision` starts at 1 and increments on every desired update; an update resets the reported lifecycle to `PENDING`, awaiting APPLIED again.
- **Idempotent retransmission**: dispatch once on create/update; after every successful gateway (re)hello, NL retransmits all specs and one bounded oldest/least-recently-attempted batch of unacknowledged explicit deletes for that gateway. Desired never disappears and reconnect automatically retries; Edge only needs to deduplicate by `(spec_id, revision)`. A leader-elected periodic sweep replays retained delete batches until the future explicit delete-ACK contract exists.
- Management plane: REST
  `GET/POST /v1/tenants/{tenant}/gateways/{gateway}/connectors` and
  `GET/PUT/DELETE …/connectors/{spec}`, permissions `connector:read` / `connector:write`;
  creation is allowed only for same-tenant devices with `is_gateway=true`.

### Instance Liveness Probe (health_check, NL → Edge)

`health_check` is an **instance-level** (not profile-template field) connectivity-probe policy, meaningful only for instances bound to a single subdevice
(non-empty `device_id`); an omitted field or `{}` disables it, and Edge MUST stop
any running probe loop for that spec. Field meanings:

- `resource`: name of the southbound resource to **read** periodically, using the same neutral resource namespace as the connector's `mappings`
  (vendor-specific URL/path semantics are forbidden).
- `interval_ms` (default 30000), `timeout_ms` (default 5000, MUST be < interval_ms),
  `fail_threshold` (default 3): probe cadence (milliseconds), per-read timeout, and consecutive-failure threshold.

Edge behavior contract:

1. Read `resource` from the bound subdevice once every `interval_ms` (GET semantics); whether the read succeeds or fails,
   **always discard the reading**: probe results MUST NOT be written to telemetry (`v1/gateway/telemetry`), shadow, or
   any reported Envelope.
2. When consecutive failures (errors/timeouts) reach `fail_threshold`: Edge autonomously declares the subdevice offline on `v1/gateway/disconnect`;
   the first subsequent successful probe declares recovery on `v1/gateway/connect`.
   connect/disconnect are state edges and MUST NOT be retransmitted every cycle.
3. Probes reflect only **application-layer connectivity to the device**, independent of MQTT transport-layer keepalive;
   stop probing immediately when the spec is deleted or `health_check` disappears.

### Deletion (NL → Edge: `v1/gateway/connectors/delete`)

```json
{"kind": "delete", "tenant_id": "…", "gateway_id": "…",
 "spec_id": "…uuid…", "device_id": "…optional uuid…", "revision": 3}
```

- Sent when explicitly unbinding/deleting a connector. NL atomically removes the desired row and commits a revisioned `connector_delete_outbox` tombstone **before** attempting the downlink. A publish failure therefore cannot erase the only delete record.
- Retained deletes are replayed in bounded, fair batches after gateway hello and by the leader-elected periodic connector sweep. Never-attempted tombstones go first, then the least recently attempted; a retained old tombstone cannot permanently starve a newer delete. `DISPATCHED` records only a transport attempt; NATS/MQTT write success is not edge acknowledgement.
- There is currently **no delete-ACK contract**. Ordinary `APPLIED` status, REST `204`, timeout, and manifest absence MUST NOT retire a tombstone. A newer same-spec desired revision atomically supersedes its older tombstone. Deleting the tenant/gateway removes the replay destination and cascades its outbox rows.
- Configuration deletion does not affect telemetry/shadow. Explicit deletion clears that spec's connector lifecycle alarms.

### State Machine (Edge → NL: `v1/gateway/connectors/status`)

```json
{
  "spec_id": "…uuid…",
  "state": "APPLIED",
  "revision": 3,
  "reason": "",
  "stats": {"success_total": 0, "p50_ms": 47.5},
  "observed_revision": 3,
  "observed_hash": "…lowercase sha256…"
}
```

```
PENDING → DISPATCHED → CREATING → APPLIED
                           ├→ FAILED (reason)
                           └→ DEGRADED
```

- Edge can receive spec/delete by subscribing to the single filter `v1/gateway/connectors/#`; status is upstream.
- NL accepts a status only when its `revision` exactly equals the current desired revision. Older and unknown-future reports are no-ops for state, optional projections, alarms, and events; status for a deleted spec remains unknown and is not a delete ACK.
- Every accepted status replaces the complete optional projection. `stats.success_total`, `stats.error_total`, `stats.p50_ms`, and `stats.p95_ms` are independently optional: an omitted field is unavailable, while an explicit zero counter is a real reading. A later omitted `stats` clears all prior measurements; a partial object does not retain omitted old fields. Counters are unsigned JSON integers and latencies are numbers in milliseconds.
- `observed_revision` and `observed_hash` are optional manager GET readback on `APPLIED`. The hash covers the complete canonical manager GET array and is distinct from manifest `reported_config_hash`/`config_hash`. Non-APPLIED status clears both fields; a desired update also resets stats and observed readback.
- Transitions carry timestamps (`dispatched_at` / `reported_at`). Same-revision metrics-only reports are valid without requiring a lifecycle transition.
- `APPLIED` / `DEGRADED` clear all escalation alarms for the spec; `FAILED` records the first-failure time.

### Escalation and Events (Reuse ADR-0019 Alarm/Notification Pipeline)

- A new desired revision still not APPLIED after **5 minutes** (`connector.pending_after`): open deduplicated alarm
  `GATEWAY_CONNECTOR_PENDING` (WARNING, dedupe key per spec).
- Edge reports `FAILED`: open deduplicated alarm `GATEWAY_CONNECTOR_FAILED` (MAJOR); still FAILED after **1 hour**
  (`connector.failed_escalation_after`): escalate once to CRITICAL.
- Both thresholds are claimed by the global sweep (default 1 minute) using atomic `UPDATE … RETURNING`, so restarts/multiple replicas trigger at most once.

### Connector Configuration JSON Schema Validation (migration 0043)

- The edge registers configuration JSON Schemas inline by `(connector_type, connector_type_version)` in hello `connectors[]`
  (see §3); the platform compiles and stores them in `connector_schema`, with retransmission performing an upsert.
- When creating/updating a connector spec: validate the profile template config as a **complete configuration** against the
  registered `(type, type_version)` schema; the instance override is a **partial patch** deep-merged onto the template,
  validated against a relaxed schema with `required`/existence constraints stripped at all levels (types/values/`additionalProperties`
  for keys actually set in the override are still validated), so an override containing one key need not include required template fields.
  Validation occurs before persistence; if the exact version is not found, fall back to the versionless `''` schema, and REST returns 400 `CONNECTOR_SPEC_INVALID` on violation.
- **fail-open**: allow a connector type for which no schema has ever been registered (validate only config object / mappings array shape),
  avoiding a chicken-and-egg problem: first gateway onboarding and profile-first configuration scenarios are not blocked.
- Schemas must be self-contained; external `$ref` is not supported (it cannot be resolved during hello).

### Connector Manifest Reconciliation and strict-reconcile (migration 0044)

The gateway's 5-minute manifest may carry a full applied `connectors[]` list (see §6). NL reconciles it against the
`connector_instance` desired set, classified as follows:

| Classification | Condition | observe (default) | strict |
|---|---|---|---|
| `in_sync` | spec exists, revision matches, hash (if reported) matches | None | None |
| `missing` | present in desired, absent from manifest | Drift alarm only | Repush existing desired spec |
| `stale` | applied revision < desired | Drift alarm only | Repush existing desired spec |
| `drifted` | same revision but `config_hash` differs | Drift alarm only | Increment desired revision **by 1**, then repush (otherwise edge `(spec_id,revision)` deduplication discards it) |
| `extra` | reported spec_id absent from this gateway's desired | Drift alarm only | Drift alarm only; no automatic delete |

- The switch is deployment-level `connector.strict_reconcile` (default `false`, observe).
- Drift in both observe/strict opens **one deduplicated alarm per gateway**, `GATEWAY_CONNECTOR_DRIFT`
  (WARNING, dedupe `gateway-connector-drift:<gateway>`, details contain spec_ids for all four classes), and clears when everything returns to
  `in_sync`. Strict corrective actions for missing/stale/drifted desired specs trigger in the same reconciliation cycle.
- `extra` is never auto-deleted, even in strict mode. A type-less manifest identity cannot safely distinguish legacy connectors from manager/filter resources, and manifest absence is not a delete acknowledgement. Only an explicit durable delete may remove those resources.
- Instances not reporting `config_hash` do not participate in `drifted` determination (existence/version only).
- `missing`/`stale` repush uses the existing desired frame; when the edge is missing/behind at an unchanged revision, it accepts normally,
  so no bump is needed; only content drift at the same revision requires a bump (see L-043 deduplication rule).
- Reconciliation is event-driven (processed immediately when a manifest arrives); a connection resides on only one node, so no additional deduplication column is needed.

### Encrypted Credential Delivery `secret://` (migration 0047)

Any string value in connector `config` may be written as `secret://<name>` to reference a secret in the current tenant:

- Secrets are managed by the control plane: `GET /v1/tenants/{tenant}/secrets` (metadata only),
  `GET/PUT/DELETE …/secrets/{name}` (permissions `connector:read`/`connector:write`).
  `PUT {"value": "..."}` writes or rotates; values are **write-only**, and no plaintext is echoed in any REST response, audit, or
  list. Naming rule: `^[a-zA-Z0-9][a-zA-Z0-9_.-]*$`.
- Ciphertext is sealed with AES-256-GCM and stored in `tenant_secret`; the KEK is a file outside the database
  (`secret-encryption.key` in the same directory as the PKI, 32 bytes; if lost, old ciphertext cannot be decrypted, so back it up with the PKI).
- NL-persisted specs / Core NATS frames / drift-hash inputs contain only **references**; plaintext is substituted only on
  the final hop before the MQTT ingress writes the downstream packet (`v1/gateway/connectors/spec`),
  and never enters configuration storage or Core NATS. Edge receives the substituted plaintext and uses it as an ordinary string.
- Reconciliation `config_hash` likewise resolves references before computing the expected hash, so the hash corresponds to the
  plaintext document actually applied by Edge, preventing specs containing secrets from permanently reporting false drift.
- If a referenced secret is deleted or its name is invalid: resolve that field to an empty string and log a warning in NL (without blocking dispatch);
  a string that is not a valid `secret://` reference (invalid name after the prefix) is passed through unchanged.

### Deferred in This Slice (Not Implemented)

- Unified plugin-version selection (`type_version` is currently entered directly through the management plane).

### Device Profile Report (`v1/gateway/profiles`)

NL defines a **vendor-neutral device model**; any edge conforming to this specification (EdgeX-based or not) reports
its point table in the same shape. Upon receipt, NL automatically merges it into the tenant-level profile library (`device_profile`, source=edge), with no manual
adopt step: identical content under the same name only refreshes the source gateway, while content drift raises an alarm without overwriting (ADR-0032).

- **Direction / QoS**: Edge → NL, QoS 1, non-retained, fire-and-forget (no ack topic).
- **Timing**: the edge replays all known profiles after every hello completes and reports a newly discovered profile immediately.
  Frames carry no tenant/gateway fields—identity comes only from the authenticated gateway connection that has completed hello.
- **Compatibility**: the fields below are extended as new optional fields. Old edges reporting only the legacy shape
  `profiles[]{name, deviceResources[]{name,valueType,units,description}}` are still accepted, with omitted fields left empty;
  both the EdgeX shape (`deviceResources`) and neutral shape (`points`) can be parsed.

#### Neutral Profile (Target Shape for Third-Party Implementations)

```json
{
  "profiles": [
    {
      "name": "acme-hvac-101",
      "protocol": "modbus",
      "description": "optional",
      "labels": ["HVAC"],
      "points": [
        {
          "name": "run_state",
          "type": "bool",
          "unit": "",
          "read_write": "RW",
          "min": 0,
          "max": 1,
          "default": "0",
          "description": "0-stop 1-run",
          "address": {"primaryTable": "COILS", "startingAddress": 0}
        }
      ],
      "commands": [{"name": "all", "points": ["run_state"]}]
    }
  ]
}
```

- **Minimum compliant set**: `name` + `points[]{name,type}`. All other fields are optional and may be added progressively according to capability.
- `type` generic enum: `bool | int | uint | float | string | binary`. Bit width is handled by the edge.
- `address`: **opaque object** describing "how to address this point under the protocol"; the NL core does not parse it. Modbus uses
  `{primaryTable,startingAddress}`, OPC-UA uses `{nodeId}`, and new protocols use custom keys.
- `protocol`: **open string** protocol family (not a closed enum), optional; omitted = unknown, NL imposes no protocol constraint,
  and the console falls back to free-form configuration. An address containing `primaryTable/startingAddress` is automatically inferred as `modbus`.

#### Protocol Family and Connector Binding

Hello `connectors[]` elements may optionally add `protocol` (protocol family) and `transports[]` (specific transport keys within the family):

```json
{"type":"modbus-tcp","type_version":"2.1","protocol":"modbus",
 "transports":["modbus-tcp","modbus-rtu"],
 "config_schema":{ }}
```

- Only when **both the library profile and connector type declare the same protocol family** does connector-spec creation strictly enforce family matching, returning HTTP 400 on violation;
  if either side omits it, validation is fail-open (console warning only), ensuring old edges/third parties/unknown protocols are not blocked.
- Profile point addressing is shared across different transports in the same family (Modbus TCP/RTU share one point table).

#### Deduplication, Drift, and Field Ownership

- `content_hash` is not transmitted on the wire; NL computes sha256 over the verbatim reported content. Same name and hash only refresh
  `profile_gateway_source.last_seen_at`; one library profile may be reported by multiple gateways (many-to-many source table).
- Same name with different hash (drift) **does not automatically overwrite**: emit an advisory (Core NATS `nl.profile.<tenant>.<gateway>`,
  kind `profile.drift`/`profile.collision`), and the operator decides whether to accept the new version; adopt with `mode:"update"` means
  "accept the version on this gateway".
- **Field ownership**: the edge owns canonical fields (`type/unit/read_write/min/max/default/address`), and replay updates only
  these columns; NL value-added fields (transform/scale/enum/breakpoints/expression/valid range) are never overwritten.
  Points deleted by the edge are not physically deleted; they are marked `inactive` to protect history and rule references.

#### Paste Import (REST, Not MQTT)

- `POST /v1/tenants/{t}/profiles/import/preview`, body `{"document": {...}}`: parse only without persisting,
  returning `{point_count, warnings[]}` (unknown types degraded to string, duplicate names skipped, etc.).
- `POST /v1/tenants/{t}/profiles/import`: parse and store as a source=import library profile; same name returns 409.
  document accepts either the neutral shape or EdgeX DeviceProfile JSON.

#### Per-Gateway Cache (Retained)

- `GET /v1/tenants/{t}/gateways/{g}/edge-profiles`: metadata for the gateway's raw report cache (`[]` when empty).
- `GET .../edge-profiles/{name}`: cache details and verbatim resources.
- `POST .../edge-profiles/{name}/adopt`, optional body `{"mode":"","target_name":""}`: default mode parses/links the
  cache row to the automatically imported same-named library profile (idempotent); `mode:"update"` forces the gateway cache content to
  overwrite drift.

### Gateway northbound filter singleton

A business northbound node carries both the NL forwarding declaration and explicit raw EdgeX selectors:

```json
{
  "channel": "meter-reading.v1",
  "forwarder_id": "…NL forwarder id…",
  "readings": ["meterId", "value", "unit", "confidence"],
  "edgex_device_name": "meter-reading-edgex-conclusions",
  "edgex_profile_name": "meter-reading-conclusion-profile",
  "edgex_resource_names": ["meterId", "value", "unit", "confidence"]
}
```

- `edgex_device_name`, `edgex_profile_name`, and a non-empty `edgex_resource_names` array are exact raw EdgeX names reported for that gateway. NL MUST NOT derive them from NL device UUIDs, canonical names, pipeline ids, or companion conclusion ids.
- Selector strings MUST be explicit. `path.Match` patterns, `PipelineJSON`, and resources with the case-sensitive prefix `Embedding` are rejected by NL and remain dropped by NE privacy guards.
- Expansion keeps each `northbound_channel` artifact as a per-contribution input, then computes one gateway-level `northbound_filter` artifact for every gateway receiving one or more contributions.
- The delivered filter is an ordinary connector spec using `connector_type="edge-northbound-filter"`, `type_version="1"`, and empty `device_id`. At most one such gateway-level spec exists per tenant/gateway. It uses the same desired/status connector transport and never introduces a second manager.
- Each contribution emits an ordered explicit `allow` rule containing its raw device/profile/resource selectors, followed by a same device/profile `deny` rule without resource names. The filter keeps `default_action="allow"`; NL does not emit broad empty selector lists.
- Reconciliation includes active and pending expansions from every business instance on the gateway. Removing one contributor updates the shared policy; removing the last contributor quiesces the retained connector with `enabled=false`, `default_action="allow"`, and `rules=[]`. It is not hard-deleted because generic node-runtime delete races are not covered by a delete-ACK contract.
- Rule forward and egress envelopes carry `channel` as business metadata. `forwarder_id` remains the stable identity that selects the JetStream stream and concrete sink.

## 8. Edge auto-provision (`v1/gateway/discovery`)

> **2026-10-12 decision: this channel is cancelled and no longer evolving** (ADR-0026 scope note).
> The mechanism below is retained in full and disabled by default, solely as history and a possible future rollback reference; it does not enter the roadmap TODO,
> and third-party edges need not implement it. If this direction is revived, this ADR section MUST first be reauthorized.

After discovering a local device on a southbound bus (Modbus/BLE/OPC UA…), the edge reports the candidate to the gateway upstream topic. When
**explicitly enabled** (setting `auto_provision.enabled: true`, default disabled), NL creates an unregistered candidate as
a subdevice bound to that gateway and returns the `local_id → device_id` mapping. The edge then uses the returned UUID through the existing
`manifest` / `connect` / `telemetry` paths; admission still relies solely on UUID validation, with no special bypass.

This is the **only exception** to the "reject if unregistered" principle, secured by four guarantees: every candidate is bound to one gateway,
only Profiles within operator policy are accepted, naming is idempotent, and each frame has a creation limit.

### Upstream Frame (Edge → NL), topic `v1/gateway/discovery`

Only connections that have completed hello negotiation and possess gateway capability may publish. `tenant` / `gateway` always come from the
authenticated connection and **are never read from the frame body**, so a gateway can provision only for itself.

```json
{
  "type": "modbus-tcp",
  "candidates": [
    {"local_id": "unit-1"},
    {"local_id": "ble-aabbcc", "name": "floor3-temp", "profile": "Modbus-Temp"},
    {"local_id": "opc-node-7", "profile": "11111111-1111-1111-1111-111111111111"}
  ]
}
```

- `local_id` (required): stable key within the edge southbound domain (unit id / address / node id). The candidate is rejected if omitted.
- `name` (optional): overrides the automatically generated canonical name; when empty, the canonical name is deterministically generated as `<gateway-canonical-name>/<local_id>`.
- `profile` (optional): UUID **or** name of a Profile in the current tenant, resolved within the tenant; cross-tenant references are always rejected;
  when empty, use the policy default Profile (`auto_provision.default_profile`).

### Downstream Frame (NL → Edge), topic `v1/gateway/discovery/result`

The edge subscribes to this fixed topic after hello (within the gateway-capability allowlist). Results are returned per candidate and may be partially successful:

```json
{
  "results": [
    {"local_id": "unit-1", "device_id": "5e46008b-…", "canonical_name": "gw/unit-1", "status": "created"},
    {"local_id": "unit-2", "device_id": "a78b5ef0-…", "canonical_name": "gw/unit-2", "status": "existing"},
    {"local_id": "stolen", "status": "rejected", "reason": "canonical name already used by another device"}
  ]
}
```

- `status`: `created` (created by this frame), `existing` (same name and already bound to this gateway; idempotently return existing UUID),
  `rejected` (candidate not created, with `reason`, without affecting other candidates), `pending` (entered the manual approval queue,
  with final `created`/`existing`/`rejected` pushed asynchronously later on the same topic; see §8 approval workflow).
- **Idempotency**: repeated reports of the same `local_id` by one gateway hit the deterministic canonical name and return the same UUID (`existing`),
  without creating duplicate devices.
- If the canonical name is already used by **another** device (bound to another gateway or unbound): reject rather than taking over the binding.

### Policy and Quotas: Deployment Defaults + Per-Tenant/Gateway Overrides (migration 0045)

Policy fields:

| Field | Default | Meaning |
|---|---|---|
| `enabled` | `false` | Master switch; when disabled, every candidate returns `rejected` and no rows are ever created |
| `max_per_cycle` | `100` | Maximum devices **created** per frame; excess candidates are rejected (existing matches do not count) |
| `max_candidates` | `1000` | Maximum candidates per frame; exceeding it fails the entire frame |
| `default_profile` | Empty | Default tenant Profile (UUID/name) when a candidate has no profile; if configured but unresolvable, the entire frame fails |
| `approval_mode` | `auto` | `auto`=create immediately; `review`=suspend candidates that "would be created" as `pending` pending operator approval (migration 0046). Same three-level inheritance and tri-state nullable fields |

**Effective policy is resolved by specificity**: gateway override → tenant default → deployment YAML (`auto_provision:`).

- Deployment YAML provides fallback defaults (the table defaults above come from it).
- Each override row stores only **fields explicitly set** (tri-state: unset=inherit the next level, while explicit `false`/`0`/`""` is a definite value).
  A gateway can therefore change only `max_per_cycle` while inheriting tenant `enabled`/`default_profile`; a gateway can also explicitly set
  `enabled:false` to disable itself even when the tenant default is enabled.
- Overrides are managed through control-plane REST (not the edge protocol):

```
GET    /v1/tenants/{tenant}/discovery-policy
PUT    /v1/tenants/{tenant}/discovery-policy            # tenant default (body contains partial fields)
DELETE /v1/tenants/{tenant}/discovery-policy            # remove tenant override and return to deployment default
GET    /v1/tenants/{tenant}/gateways/{gateway}/discovery-policy
PUT    /v1/tenants/{tenant}/gateways/{gateway}/discovery-policy
DELETE /v1/tenants/{tenant}/gateways/{gateway}/discovery-policy
```

  GET returns the effective policy (all levels folded) + `overridden` flags; PUT must carry at least one field, and `max_*` must be positive integers;
  the gateway must be an is_gateway device in that tenant (otherwise 400). Permissions: GET requires `device:read`; PUT/DELETE require
  `device:write`.

Creation reuses all `CreateDevice` guards: tenant device quota, Profile ownership, ownership/gateway
validation, and registration history. Whenever a frame creates any device, write one `CONFIG_CHANGE / auto-provision` audit and emit a
`discovery.provisioned` summary advisory on Core NATS `nl.discovery.<tenant>.<gateway>`.
This slice does not force devices online: after creation, presence converges naturally on the next `connect`/`manifest`.

> Manual approval: when effective `approval_mode=review`, candidates that would create devices do not do so immediately; instead they are suspended as `pending`
> in the `discovery_candidate` queue (migration 0046). Existing same-name matches still return `existing` immediately,
> and conflicting/invalid candidates still return `rejected` immediately. Operators approve through the control plane
> (`GET /v1/tenants/{t}/discovery-candidates`, `.../{id}/approve|reject`, requiring
> `device:read/write`); approval creates the device through the same CreateDevice guards, and NL then asynchronously pushes the final result for that local_id to the gateway on the **same**
> `v1/gateway/discovery/result` topic (discarded while the gateway is offline; the next discovery naturally resolves to `existing`, so delivery is best-effort). Only one PENDING is retained per
> (gateway,local_id) at a time: repeated discovery idempotently returns `pending`;
> once the candidate reaches a terminal state, a later discovery is allowed
> to suspend it again.

## 9. On-Demand Probes (Application → NL, HTTPS; NL → Edge, MQTT)

An application requests immediate reachability/reading probes for a batch of gateway subdevices. NL groups devices by owning gateway and dispatches
**one aggregated frame** to each online gateway; execution is asynchronous, and REST immediately returns 202 + task. The platform does not interpret probe semantics: both `mode` and
device `result` are passed through opaquely.

### REST (Application → NL)

```
POST /v1/tenants/{tenant}/probes
  Header: Authorization: Bearer ... ; Idempotency-Key: <optional>
  Body: {"devices": ["dev-a","dev-b"], "mode": "fresh", "timeout_ms": 10000}
→ 202 {
     "id":"<task_id>", "tenant_id":"...", "mode":"fresh", "timeout_ms":10000,
     "state":"pending", "total_count":2, "succeeded_count":0, "failed_count":0,
     "created_at":"..."
   }

GET  /v1/tenants/{tenant}/probes?page=&page_size=      # paginate tasks (newest→oldest)
GET  /v1/tenants/{tenant}/probes/{task_id}             # task aggregate status
GET  /v1/tenants/{tenant}/probes/{task_id}/items       # per-device results (including result/error)
```

- Permissions: write `probes:write`, read `probes:read` (ENGINEER and TENANT_ADMIN have read/write;
  CUSTOMER_USER has read/write; READ_ONLY has read-only). Service accounts receive these through scopes, which must be in the 0041 allowlist.
- Targets must be same-tenant, ACTIVE/UNCLAIMED subdevices **bound to a gateway**; unbound/inactive/unknown ids
  return 400, and no batch is created.
- mode: `cached / fresh (default) / strict`, validated and passed through only; `timeout_ms` defaults to 10000.
- Idempotency: a retry with the same `Idempotency-Key` and body replays the original 202; the same key with a different body returns 409.
- Default protective quotas (configuration `probe:`; all use local in-process counters, consistent with the no-Redis architecture):
  - At most 100 devices per task (excess returns 400 `PROBE_TOO_MANY_DEVICES`);
  - Creation rate of 1 QPS per principal (429 `PROBE_RATE_LIMITED`);
  - At most 5 unfinished tasks per principal (DB count, 429 `PROBE_CONCURRENCY_LIMITED`);
  - 10s cooldown per device (429 `PROBE_COOLDOWN`).
- **Request coalescing**: check before quotas—if all requested devices already belong to one unfinished (pending/running) task for the **same principal and
  same mode**, and their corresponding items are still unfinished, directly replay that in-flight task (return the same 202 task) without consuming QPS/concurrency/cooldown quota or dispatching again. Partial overlap (some devices
  not in the same in-flight task) is not coalesced; create a new task normally (which may trigger cooldown). Only in-flight tasks can be coalesced;
  recent results from finished tasks are still subject to cooldown,
  rather than being coalesced.
- **Data scope**: target resolution and task/item reads are narrowed by the caller's RBAC data scope (CUSTOMER/GROUP),
  consistent with alarm/device reads; out-of-scope devices are rejected as invalid targets at creation (400), and out-of-scope tasks are treated as invisible
  (404).
- Results are retained for 24h; a sweep (default 1m) physically deletes tasks and their items by `finished_at`.

### Result Push (WS)

Task/per-device progress is pushed to WS resource `probe_task` (subscription requires `probes:read`), with frames shaped like batch commands:

```json
{"type":"probe_task","id":"<sub>","seq":12,"data":{
  "type":"item",
  "task":{"id":"...","state":"running", ...},
  "item":{"task_id":"...","device_id":"...","state":"succeeded","result":{...}}
}}
```

For terminal `type:"task"`, `task.state` is `completed / partial / failed`.

### MQTT（NL ↔ Edge）

- Downstream (NL→Edge, topic `v1/gateway/probe`, gateway subscribes): devices in the same task and gateway are aggregated into one frame.

```json
{"probe_id":"<task_id>","devices":["dev-a","dev-b"],"mode":"fresh","timeout_ms":10000}
```

- Upstream (Edge→NL, topic `v1/gateway/probe/response`, per-device or batch report; gateway
  capability, requires hello negotiation). Both frame forms are accepted:

```json
{"probe_id":"<task_id>","device":"dev-a","result":{"reachable":true,"rtt_ms":12}}
{"probe_id":"<task_id>","device":"dev-b","error":"no response"}
```

A batch frame uses `responses[]` to report multiple devices at once; an entry may omit `probe_id`, inheriting the top-level frame value by default:

```json
{"probe_id":"<task_id>","responses":[
  {"device":"dev-a","result":{"reachable":true,"rtt_ms":12}},
  {"device":"dev-b","error":"no response"}
]}
```

- Correlation key `probe_id == task_id` + `device`; duplicate/late results for a device take effect only once on a running item.
- **Gateway offline fails immediately**: after grouping, look up gateway presence; if offline, directly mark its devices `failed`
  (`gateway not connected`) without dispatching; downstream write failures are handled the same way.
- Task deadline: default 60s (and at least `timeout_ms + 2s` round-trip margin); devices still pending/running at the deadline
  are marked `failed` (`probe did not complete in time`), and the task finishes.
- Restart recovery: items left running by the previous process can no longer receive reports and fail at startup; pending tasks are regrouped and redispatched.
- Cross-request result coalescing, upstream `responses[]` batch reports, and CUSTOMER/GROUP data-scope drill-down
  are all implemented (see above). Edge currently still produces per-device frames; batch frames are a platform-first compatibility capability, and enabling them on Edge
  requires no platform change.

## 10. Blobs and OTA (HTTPS Relay)


### Device Media BlobRef (Implemented)

Binary media such as device images bypasses time-series storage: bytes go to the blob backend, and `ts_telemetry` stores only a
`blob://<key>` string reference, with no bytea column or database migration. Two upstream methods:

1. Direct binary upload: `POST /v1/me/blob` (device credentials; `?key=<measurement-key>`, default `blob`; keys allow only
   `[A-Za-z0-9_.-]{1,128}`). The server generates the object key, responds with
   `{published,key,uri,size}`, and automatically publishes the corresponding telemetry point. Download: `GET /v1/me/blob?key=...`,
   permitting access only to the device's own objects and supporting Range/ETag/conditional requests.
2. Telemetry-frame marker: write the field as
   `{"blob":true,"content_type":"image/jpeg","filename":"x.jpg","data":"<base64>"}`;
   standard/URL-safe base64 is accepted (padding optional). This works over both HTTP and MQTT, and can also be used in subdevice values within gateway
   `v1/gateway/telemetry`; object keys are generated according to subdevice identity.

Object-key layout: `media/<tenant>/<device>/<uuid>`. Console users (permission `device:read`) obtain a short-lived download URL through
`GET /v1/tenants/{tenant}/blob/sign?key=...` (S3 presigning, or an HMAC-signed `/v1/blobs/get` for the local
backend). Policy: default 10 MiB per object, allow `image/`, configured through
`blob.media_max_bytes` / `blob.media_allowed_types`; when `content_type` is empty, do not guess it.
When blob is disabled, marker fields are explicitly rejected and never inlined.

### Blob Upstream (S3 Invisible to Edge)

1. `POST /v1/connector/<edge-id>/uploads` (multipart/streaming chunks, resumable upload, connector credentials).
2. NL streams to S3 (without writing to local disk), assembles chunks, and computes sha256.
3. On completion, produce a BlobRef message (endpoint+bucket+key) into the normal telemetry pipeline.
4. Optional direct upload to S3 with presigning is available only when network policy permits.

### OTA (migration 0048: External Firmware URL, Implemented)

> **2026-10-12 scope decision (ADR-0037 Accepted): OTA is for direct devices only.** OTA for the gateway itself and gateway-managed subdevices
> has been removed; the gateway `v1/gateway/ota/*` relay mechanism below is retained only as dormant history, and NereidEdge no longer implements
> the corresponding edge side; if a third-party edge requires it, implement the direct-device pull protocol (`/v1/me/ota/*`, see ADR-0037 and
> `internal/ingesthttp/ota_handler.go`) itself.

The currently delivered OTA slice does not relay firmware bytes, only **descriptors and progress**:

1. Control plane `POST /v1/tenants/{t}/ota-tasks` (permission `device:write`, idempotency key replayable) submits
   `{devices:[...], package:{version,url,sha256,size,headers?}}` and returns 202 + task id.
   `url` must be an absolute `http(s)` address, and `sha256` must be 64 hexadecimal characters; targets must be
   ACTIVE/UNCLAIMED subdevices bound to a gateway, at most 1000 per request.
2. NL groups by owning gateway and dispatches one frame to each online gateway's unique connection:
   `v1/gateway/ota/task`:
   `{task_id, devices[], version, url, sha256, size, headers?}`. Pending targets on an offline
   gateway are immediately marked `failed` at dispatch (`gateway not connected at dispatch`) rather than left hanging.
3. Edge downloads directly from `url` (may include `headers`, such as authorization headers), and **MUST verify sha256 successfully before upgrading**.
4. Edge reports per device on `v1/gateway/ota/progress`:
   `{task_id, device, state, progress_pct, message?}`, with case-insensitive state:
   `DOWNLOADING / DOWNLOADED / UPDATING / SUCCESS / FAILED` (internally lowercase, `SUCCESS→succeeded`).
   Progress states never regress (a late `downloading` after `updating` is ignored), `progress_pct` is monotonically nondecreasing,
   and duplicate/late terminal frames no longer change the result.
5. Task aggregate state `pending → running → completed/partial/failed`; progress is queried with pagination through
   GET `/ota-tasks[/{id}[/items]]` or pushed through WS resource `ota_task` (`nl.ota.task.>`).
   OTA is a long-running operation with no 24h result cleanup; after restart, open tasks redispatch targets still pending.

### OTA Still Deferred

- S3 HTTPS relay (blob relay, ADR-0006) and platform-hosted firmware bytes.
- Edge agent self-upgrade task type `target=edge-agent`; centralized batch scheduling such as batches/canary/failure thresholds.

## 11. Command Downstream and direction (read/write)

Commands must first be declared in the device **command catalog allowlist**; NL returns
404 for an undeclared command name and does not dispatch it. Each allowlist entry carries interaction mode (`one-way` / `request-response`), timeliness
(`realtime` / `persistent`), default timeout, and independent read/write masks (`allow_read`/`allow_write`);
masks may be materialized automatically from bound-profile measurement `read_write` (R/W/RW) or maintained manually.

### Downstream Frame (NL → Edge: `v1/gateway/command`)

```json
{
  "command_id": "…uuid…",
  "device": "…sub-device-id…",
  "method": "camera_status",
  "direction": "read",
  "interaction": "request-response",
  "timeliness": "realtime",
  "params": {}
}
```

- `direction` ∈ `read|write` is a second dimension **orthogonal** to `interaction`:
  - `interaction` only indicates whether to wait for a result response (one-way has no response);
  - `direction` indicates southbound operation semantics: `read` MUST perform a GET/resource read, and `write` MUST perform a
    PUT/resource write. Edge **MUST NOT infer direction from method again** and MUST execute strictly according to the frame field.
  - `one-way` does not allow `read` (reading and discarding the result is meaningless), enforced in both the allowlist and send API.
- `read` likewise **commonly carries explicit `params`** (default `{}`): read commands may include query parameters, and Edge SHOULD NOT assume
  read has no parameter body.
- Responses continue to use `v1/gateway/command/response` (`command_id`, `device`, `data`);
  one-way has no response frame.
- Direct-device frames `v1/me/cmd/<name>` likewise carry `direction` with identical semantics.

## 12. Edge Secret Delivery (ADR-0034)

The authoritative copy of each secret in the platform vault (tenant vault) resides on the platform; gateways hold only replicas. Delivery is **declarative
desired/reported**: the platform maintains the desired state of each binding, and the gateway idempotently applies full frames and reports back.

### Capability Bit

- Hello `features` adds optional capability `secrets`. The platform includes it in the supported list and writes it to
  Ack/Enabled; the most recently negotiated capability set is stamped onto the gateway device row (`agent_features`).
- For gateways that have not negotiated `secrets`: REST can still record bindings, but the platform **does not dispatch them**, and the console clearly displays
  "firmware not supported"; after a firmware upgrade, hello redrive automatically backfills them.

### Full desired (NL → Edge: `v1/gateway/secrets/sync`)

After every save and every successful hello, the platform sends the **complete set** to that gateway (idempotent, QoS1):

```json
{
  "tenant_id": "…uuid…",
  "gateway_id": "…uuid…",
  "entries": [
    {
      "name": "camera-admin",
      "type": "onvif-basic",
      "version": "1",
      "revision": 3,
      "removing": false,
      "selectors": [{"kind": "mac", "value": "aa:bb:cc:dd:ee:ff"}],
      "document": {"username": "admin", "password": "…plaintext…"}
    }
  ]
}
```

- `selectors` is a generic structure `[{kind,value}]`; the platform does not interpret semantics or impose uniqueness constraints:
  omitted means the whole gateway; one binding may contain multiple selectors, and the same value may appear in multiple bindings.
  The first kind defined by the integration document is `mac`: it binds the secret to the device with the corresponding MAC;
  "how to use it after binding" is entirely Edge's implementation (the platform does not validate MAC format or reconcile it).
  Future new kinds need only be registered in the integration document, with no platform change.
- `revision` increases monotonically from 1. Multiple offline modifications are coalesced into one row, and only the latest revision is delivered;
  gateways deduplicate by `(name, revision)`.
- `removing=true` means revocation, and the gateway erases the replica; document is omitted in this case.
- The gateway does not autonomously delete existing replicas absent from the set (a full frame covers only this gateway in this tenant; deletion
  always uses explicit `removing`).

### Security: References and Last-Hop Resolution

- In frames on Core NATS channel `nl.edge.secret.desired.<tenant>.<gateway>`, secret fields appear only as
  references: `secret://<name>#<field-path>`. Core NATS does not persist plaintext.
- On the **last hop** before writing the downstream packet, the MQTT relay opens the vault documents in batch and replaces references with plaintext, writing only into
  the single MQTT packet destined for that gateway (mirroring connector `secret://` last-hop substitution, migration 0047).
- Therefore, the document Edge receives on `v1/gateway/secrets/sync` already contains plaintext; Edge MUST encrypt it before local persistence
  and MUST NOT persist it in plaintext or emit it to logs.

### State Machine (Edge → NL: `v1/gateway/secrets/status`)

```json
{
  "reports": [
    {"name": "camera-admin", "revision": 3, "status": "APPLIED", "reason": ""}
  ]
}
```

- Upstream status ∈ `APPLIED|FAILED|REMOVED`. `FAILED` uses `reason` for a concise, transport-safe
  failure description; `REMOVED` completes one revocation.
- Platform-side state: `PENDING → DISPATCHED → APPLIED(/FAILED+reason)`, revocation
  `REMOVING → REMOVED`. PENDING/DISPATCHED/REMOVING are platform-internal states that Edge MUST NOT report.
- The topic is fire-and-forget: malformed frames or unknown bindings are only logged, with no error returned to Edge.
- Every state change is pushed to the console through event channel `nl.secret.event.<tenant>` (WS resource
  `secret_binding`), and the console rereads the binding list accordingly.

### Alarms

- A binding remaining in PENDING/DISPATCHED for more than 5 minutes: open a WARNING not-applied alarm.
- Persistent FAILED: initially open MAJOR, escalating to CRITICAL after 1 hour. An atomic UPDATE claims the escalation, so it occurs at most once across
  replicas/restarts; APPLIED or REMOVED clears related alarms.

## 13. Gateway Operation Invocation (ADR-0035)

A Gateway Operation is an on-demand immediate action **acting on the whole gateway** (for example, reboot or a vendor maintenance
routine). It is neither connector desired (long-lived configuration) nor a subdevice command (see §11). The platform
has no built-in operation vocabulary: when invoking a gateway, invocability, parameter schema, and risk level come only from **descriptors advertised in that gateway's own
hello** (§3, stored per gateway); only when the target gateway has not advertised one does the platform fall back to a tenant-private descriptor.

### Invocation Frame (NL → Edge: `v1/gateway/operations/invoke`)

```json
{
  "id": "1f4e0d77-....",
  "operation": "vendor.reboot",
  "type_version": "1",
  "params": {"delay_seconds": 5},
  "timeout_ms": 30000
}
```

- The platform side is synchronous request/reply: persist the task, dispatch it, and wait for a result until the effective timeout—the smaller of the
  descriptor default and this invocation's downscaled value (`timeout_ms`), clamped to
  100ms..60s; timeout is recorded as `TIMEOUT`.
- A gateway **fails immediately while offline** with `NOT_CONNECTED` and is never queued; use commands when delivery after reconnect is required.
- Edge need only execute operations advertised in its own hello; `params` has already been validated against the descriptor, and parameters
  and results are each limited to 64KB per frame.
- `secret://<name>` (and `#<field>`) in parameters is resolved to plaintext by the relay on the last hop, using the same rules
  as §12; Edge MUST NOT log or persist resolved values.

### Result Frame (Edge → NL: `v1/gateway/operations/result`)

```json
{"id": "1f4e0d77-....", "ok": true, "result": {"uptime_before_s": 12345}}
```

- When `ok=false`, provide a concise, transport-safe failure description in `error`, and record the task as `FAILED`.
- One-way descriptor: the platform records success immediately after sending invoke and does not wait for result.
- Late/duplicate results (unknown `id`) are logged and discarded without changing task state.
- **Protocol contract: result MUST NOT contain passwords**: the platform does not inspect result content, and Edge is responsible for redaction before reporting.

### Tiered Gates and Audit Trail (Platform Side)

- Risk level comes only from the descriptor: `read` requires only permission; `normal` requires genuine secondary confirmation in the UI;
  `dangerous` requires a human account + one-time TOTP step-up within 5 minutes (work item 2, L-090).
- Operation routes at all risk levels are human-only: machine (service-account) identities are always rejected with 403 `OPERATION_HUMAN_ONLY` for read/normal and
  dangerous; related scopes cannot be granted to service accounts.
- A dangerous invocation rejected before step-up (machine identity, missing step-up, or failed validation) writes a GATEWAY_OPERATION audit
  (`action=invoke_denied`) even if no task was created.
- A descriptor disabled by the tenant cannot be invoked; the platform does not infer risk from names.
- Before dispatch, the platform validates parameters against descriptor `param_schema`; invalid parameters are rejected with 400
  `OPERATION_PARAMS_INVALID`, with no task persisted and no dispatch.
- Task results are retained for 90 days and cleaned by a background sweep; chained audits permanently record operator, time, gateway, action,
  risk level, and outcome, **without recording parameter or result content**.

## 14. Device Profile Downlink (ADR-0038)

The tenant `device_profile` library is the **sole content source** for device Profiles (ADR-0032). This slice expresses only
"**which library entry is delivered to which gateway**" and never copies Profile text: `A1` reported by gateway A is a tenant
asset that gateway B can reuse directly without rewriting it.

Downlink documents are generated by the cloud in the **rendering format** declared by the gateway, and the core carries no protocol-specific concepts; `nereid-
neutral/1` is always available, while `edgex-device-profile/3` is only a cloud-side adapter.

### Capability Bit and Format Negotiation

- A gateway declares support for this slice by including `profiles` in hello `features`; gateways that do not declare it **never**
  receive downstream frames, leaving old firmware unaffected.
- A gateway may include `profile_formats` (**ordered** preferences, for example `["edgex-device-profile/3",
  "nereid-neutral/1"]`). Ack `profile_formats` echoes the formats the platform can render from the **intersection** with that gateway;
  when undeclared, fall back to `nereid-neutral/1`.
- The platform persists this intersection per gateway as the rendering basis.

### Hello Extension (Edge → NL, topic `v1/gateway/hello`)

```json
{
  "v": 1,
  "edge_id": "gw-b",
  "features": ["telemetry", "profiles"],
  "profile_formats": ["edgex-device-profile/3"]
}
```

### Ack Extension (NL → Edge)

```json
{
  "status": "ok",
  "features": ["telemetry", "profiles"],
  "profile_formats": ["edgex-device-profile/3"]
}
```

### Full desired (NL → Edge: `v1/gateway/profiles/spec`)

The frame is the **full target set**: it contains all Profiles the gateway should hold (`explicit ∪ connector-instance references`)
and entries currently in `REMOVING` that Edge must revoke. Each `document` has already been rendered by the cloud in the
negotiated format, and Edge applies it directly.

```json
{
  "tenant_id": "8e1f....",
  "gateway_id": "5c2a....",
  "entries": [
    {
      "profile_id": "a1b2....",
      "name": "A1",
      "revision": 2,
      "format": "edgex-device-profile/3",
      "target": {"service": "device-modbus"},
      "document": {
        "name": "A1",
        "deviceResources": [
          {
            "name": "temperature",
            "properties": {"valueType": "Float32", "units": "Cel", "readWrite": "R",
                           "minimum": -40, "maximum": 150},
            "attributes": {"slave_id": 1, "function": 3, "offset": 10}
          }
        ],
        "deviceCommands": [
          {"name": "read_all", "readWrite": "R",
           "resourceOperations": [{"deviceResource": "temperature"}]}
        ]
      }
    },
    {"profile_id": "c3d4....", "name": "Old", "revision": 1,
     "format": "edgex-device-profile/3", "removing": true}
  ]
}
```

- `format` is the format used for the entry; `document` is the **cloud-rendered result**, and Edge MUST NOT assume its format comes from
  any fixed field—use `format`.
- `target` is an **optional, opaque** hint (such as target device-service name), derived by the protocol family through the global
  protocol catalog; the core does not interpret it, and Edge may ignore it.
- Idempotency: Edge deduplicates by `(name, revision)` and may directly acknowledge a received revision ≤ its locally applied revision.
- With `removing=true`, `document` is **omitted**; Edge should delete the local Profile and report
  `REMOVED`.
- Revocation has a **reference fallback** rule: dispatch `removing` only when explicit distribution has been removed and no connector instance on that gateway still references the
  Profile.

### State Machine (Edge → NL: `v1/gateway/profiles/status`)

```json
{
  "reports": [
    {"name": "A1", "revision": 2, "status": "APPLIED", "reason": ""}
  ]
}
```

- Upstream status ∈ `APPLIED|FAILED|REJECTED|REMOVED`; `FAILED`/`REJECTED` uses `reason` for a
  concise, transport-safe description.
- Platform-side state: `PENDING → DISPATCHED → APPLIED(/FAILED|REJECTED)`, revocation
  `REMOVING → REMOVED`. PENDING/DISPATCHED/REMOVING are platform-internal states that Edge MUST NOT report.
- The topic is fire-and-forget: malformed frames or unknown entries are only logged, with no error returned to Edge.
- Every state change is pushed to the console through event channel `nl.profile.event.<tenant>`, and the console rereads the gateway's
  Profile list accordingly.

### Alarms

- The latest desired revision remaining in PENDING/DISPATCHED for more than 5 minutes: open a WARNING not-applied
  alarm (`GATEWAY_PROFILE_PENDING`).
- Persistent FAILED/REJECTED: initially open MAJOR (`GATEWAY_PROFILE_FAILED`), escalating to CRITICAL after
  1 hour. An atomic UPDATE claims the escalation, so it occurs at most once across replicas/restarts; APPLIED or REMOVED clears related
  alarms.

### Content revision and Desired Hash

- Library Profiles add `revision` (monotonic content version) and `desired_hash` (canonicalized
  sha256 of the rendered projection). `desired_hash` covers only the Edge-visible projection (name/protocol/description/labels/
  points/commands); **operational value-added fields (transform/scale/enum/range validation, etc.) do not participate in the projection
  and do not trigger revision increments**.
- Increment `revision` only when the rendered projection changes; reasserting desired with an unchanged projection causes no unnecessary redelivery.
- This differs from existing `content_hash` (hash of the verbatim upstream payload used for drift detection); both
  coexist with independent purposes.

### Console REST (Application ↔ NL, HTTPS)

- `GET/POST /v1/tenants/{tenant}/profiles/{profile}/targets`: list/add shared library distribution
  targets (explicit distribution, request body `{"gateway_id": "..."}`).
- `DELETE /v1/tenants/{tenant}/profiles/{profile}/targets/{gateway}`: remove explicit distribution.
- `GET /v1/tenants/{tenant}/profiles/{profile}/deliveries`: view delivery status across gateways by Profile.
- `GET /v1/tenants/{tenant}/gateways/{gateway}/profile-deliveries`: view per-Profile
  delivery status for this gateway.
- The routes above reuse `profile:read` / `profile:write` for RBAC.

## 15. Edge Model Inference (ADR-0039)

This section defines the wire protocol for cloud-side Phase A of edge model inference. Core principles: **NL does not relay model files, initiate inference
calls, or interpret label semantics**; the gateway reports local model inventory in the optional manifest `models` section, and NL persists/
reconciles/displays that view and raises alarms across three state planes. Without negotiated capability, the edge sends no `models` section and receives no
`edge-inference` spec, behaving byte-for-byte like old firmware.

### 15.1 Capability Negotiation (hello / ack)

Declare `"inference"` in Hello `features.optional` and add a top-level optional `inference` block; when the capability is accepted, Ack
**echoes the intersection**. An omitted block or empty intersection means the cloud does not accept it and the edge does not enable it (the same
intersection-based go/no-go model as profiles):

```json
// Hello (Edge → NL)
{
  "features": {"required": ["telemetry", "presence", "command"],
               "optional": ["shadow", "profiles", "inference"]},
  "inference": {"contract": "model/1", "backends": ["kserve", "openai"]}
}
// Ack (NL → Edge, when accepted)
{ "status": "OK", "features": ["…", "inference"],
  "inference": {"contract": "model/1", "backends": ["kserve", "openai"]} }
```

- `inference.contract`: model/inference contract version implemented by the edge, currently only `model/1`; on contract mismatch,
  the feature is not enabled (the entire `inference` block is omitted from Ack).
- `inference.backends[]`: enum of **protocol families** the edge can speak (`kserve` | `openai`, future
  `task-runtime`), not vendor names, and does not indicate that any particular server instance is online; Ack echoes the **intersection while preserving edge
  declaration order**. An empty intersection likewise does not enable the feature.
- NL records the negotiation result (contract + backends intersection) in the gateway device row (migration 0086
  `device.agent_inference`); when not negotiated, it is an empty object `{}`, and the runtime watchdog considers only
  gateways that actually accepted inference.

### 15.2 Full Manifest `models[]` Section

An optional section alongside `devices` and `connectors` (see the frame example in §6). Its semantics match the `connectors` section:

- **Omitted field** (`models` key absent, old edge/not negotiated): NL performs no model reconciliation, retains stored inventory unchanged,
  and generates no missing drift. **An edge that has negotiated inference may omit this section only when "not negotiated/reading NI failed"**;
  after successfully reading zero inventory, it MUST explicitly send `[]`. Continuously sending only device/connector sections while omitting the models section is caught by the section-level
  stale watchdog (see 15.5; inventory is marked stale and alarmed after 15 minutes).
- **Explicit `"models": []`**: authoritative zero-inventory report; hard-delete all inventory rows for the gateway (one prune
  audit per model). It MUST be sent when all runtime models are unloaded, rather than omitting the section.
- A non-empty list is a **full replacement**: the in-frame list = expected inventory; upsert by `(tenant, gateway, id, version)`;
  models disappearing from the list are **pruned directly** (models are not presence entities and do not "transition to OFFLINE"),
  and each pruned model writes one persistent `event='pruned'` audit row in `gateway_model_inventory_event`.
- Reuse the `gw-manifest` lease in §6 (approximately 3 cycles): on lease expiry, mark inventory rows `stale` (**retain, do not
  delete**) and clear the mark after the gateway resumes reporting. Stale models cannot be used for new bindings.

| Field | Required | Description |
|---|---|---|
| `id` / `version` | Yes | Model identity and semantic version; `(gateway,id,version)` is the inventory key; if either is missing or blank, reject the entire frame |
| `revision` | No | Build/optimization task id (string, such as `"76937"`), used for idempotency/traceability |
| `task` | Yes | Open enum: `detection`/`classification`/`segmentation`/`pose`/`ocr`/`chat`/`embeddings`/`custom`; other values are passed through verbatim |
| `family` | No | Result/post-processing family within the task (for example, `yolov8`); determines point table and detail schema |
| `backend` | Yes | Inference protocol family `kserve`/`openai`/`task-runtime` |
| `server_family` | No | Concrete model-server product serving this model, as an open enum passed through verbatim (e.g. `ovms`/`triton`/`external`). Distinct from `backend`, which is a wire protocol rather than a vendor/product token. Omitted by firmware predating the field; NL stores `''` and the console falls back to `backend` for display. Adding the optional field does not change the `model/1` contract: older NL builds ignore the unknown JSON key, and edges that omit it keep their existing inventory rows unchanged. |
| `model_name` | No | Model name used when requesting the server, for display/diagnostics only |
| `state` | Yes | `EXTRACTING` / `VALIDATING` / `READY` / `FAILED` / `REMOVED`; an unrecognized state rejects the entire frame |
| `reason` | No | Failure reason code (see 15.6); empty string on success |
| `labels` | No | Array of class names whose indices are class ids; business data is stored/displayed verbatim, **without i18n or core interpretation** |
| `active_bindings` | No | Number of references from this gateway's edge-inference instances (edge-authoritative) |

### 15.3 `edge-inference` Connector (Zero Core Special Cases)

- The edge self-registers `connector_type="edge-inference"`, `type_version="1"` through hello `connectors[]`;
  its config JSON Schema is supplied by the edge and compiled/stored by NL (existing ADR-0026
  connectorcatalog mechanism).
- desired still uses `v1/gateway/connectors/spec`; `device_id` is required and points to a virtual output subdevice that owns inference-result telemetry
  (see 15.4). The config shape is opaque to the core:

```json
{
  "source":    {"device": "<camera-subdevice-UUID>", "resource": "snapshot_jpeg", "mode": "snapshot"},
  "model_ref": {"id": "yiqisoft-yolov8n", "version": "1.0.0", "revision": "76937"},
  "trigger": "event",
  "period_ms": 1000,
  "max_idle_ms": 60000,
  "error_threshold": 5,
  "conf_threshold": 0.25,
  "target_device": "CPU",
  "emit_frame": true,
  "annotate_preview": true,
  "ffmpeg_extra": ""
}
```

Evidence frames and ffmpeg tuning (both optional; when omitted, the NE bridge supplies legacy binding behavior):

| Field | Type/Default | NE → NI Property | Semantics |
|---|---|---|---|
| `emit_frame` | bool, default `true` | `EmitFrame` | Whether each result event includes an evidence JPEG (`FrameJPEG` reading); disabling saves upstream bandwidth/storage but leaves no image for drill-down |
| `annotate_preview` | bool, default `true` | `AnnotatePreview` | Whether to draw detection boxes/labels on the evidence image and local diagnostic preview (§15.7); independent of whether an image is attached |
| `ffmpeg_extra` | string, ≤256, default empty | `FFmpegExtra` | ffmpeg stream acquisition (`mode=stream` or rtsp/rtsp-udp/mpjpeg/jpeg with `mode=url`); space-separated argv fragment, **no shell, no quoting**, with the URL always a separate argument. Allowlist: `-re` and value-taking `-r/-ss/-t/-threads/-fflags/-flags` (for example, `-fflags nobuffer -flags low_delay`); anything else is rejected by NI authoritative validation (`config-invalid`) |
| `decode_accel` | enum `software`/`vaapi`, default `software` | `DecodeAccel` | Site-local ffmpeg input decoding for `mode=stream` (`onvif-camera`) and direct `rtsp`/`rtsp-udp` only. Snapshot, MJPEG and JPEG sources reject `vaapi`. The console omits the software default; hardware decode is never encoded in `ffmpeg_extra` |
| `vaapi_device` | optional string, `^(?:/dev/dri/)?renderD\d+$` | `VAAPIDevice` | DRM render node for `decode_accel=vaapi`; short and absolute forms are passed unchanged by NL and normalized by NI. Empty/omitted selects NI's `/dev/dri/renderD128` default. A device without `vaapi` is invalid |

The console displays corresponding controls only when the self-registered schema declares these properties; boolean values at their default (true) are not dispatched,
and `ffmpeg_extra` is dispatched only when non-empty in stream/url mode, preserving byte compatibility with old firmware. Decode controls are hidden for non-RTSP sources,
software decoding omits both new keys, and a missing VA-API driver/device fails explicitly (`source-no-frame`) without silently falling back to software. The host must provide
the VA-API driver and `/dev/dri` access (for example the `intel-media-driver` package and container device mapping, or the Kubernetes `gpu.intel.com/i915` resource).

`source.mode` (optional; omitted is equivalent to `"snapshot"`, so old bindings are fully backward compatible)—frame-acquisition method.
For the two ONVIF modes, stream URLs and credentials are always resolved at the edge; `mode=url` is the only exception carrying a URL (address only,
no credentials; see table below):

| mode | NI SourceKind Mapped by NE | Frame-Acquisition Method |
|---|---|---|
| `snapshot` (default) | `onvif-snapshot` | Invoke the ONVIF `Snapshot` command through core-command each cycle to obtain one JPEG |
| `stream` | `onvif-camera` | NI resolves the RTSP URL through edge federation (core-metadata protocol properties + `GetStreamUri` + the camera's own
  EdgeX secret), and ffmpeg decodes continuously; use the latest frame for inference at each trigger cadence |
| `url` | `transport` value: `rtsp`/`rtsp-udp`/`mpjpeg`/`jpeg` | **Escape hatch for cameras without ONVIF registration**:
  omit `device`/`resource` and instead supply direct `url` (NE skips the camera resolver, dispatches `SourceURL`, and
  does not dispatch `SourceDevice`); credentials use a named secret provisioned at the edge (`secret_name` → NI `SecretName`) |

`source.profile` (optional, `mode=stream` only, string, ONVIF Media ProfileToken,
`^[A-Za-z0-9_.:,-]+$`, ≤64; omitted = camera default profile, usually the main stream):

- NE passes it through as NI Job property `StreamProfile`; NI federation invokes the read-only `StreamUri`/`GetStreamUri`
  resources by token, with the token delivered through the base64 `jsonObject` query parameter (`{ProfileToken, StreamSetup}`)
  (device-onvif-camera 4.x rejects PUT and ignores other query keys);
  main/sub streams are resolved and cached separately (cache key `(camera, token)`), and 401/stream-start failure invalidates the camera as a whole.
- The optional token set is enumerated by the edge read-only operation `camera.profiles` v1 (see §15.7);
  the console shows a dropdown when acquisition is video stream and the schema declares `source.profile`; on enumeration failure, manual token entry is allowed
  and passed through verbatim. The token does not apply to snapshot mode (snapshot uses the Snapshot command and does not accept profile), and
  NE/NI directly returns `config-invalid` for invalid combinations.

For managed ONVIF sources, the console derives output identity from camera + optional profile + model id/version. An explicit profile adds
`profile-<profile-hash8>` to the virtual device name (`inference:<source>:profile-<profile-hash8>:<model-id>:<model-version-hash8>`); camera-default
sources retain the previous name without that segment. Different profiles of one camera can therefore run the same model version independently, while
one profile can run multiple model versions. Exact semantic rebinds still reuse devices named before profile-aware naming and preserve their aliases.

Direct `source` fields (`mode=url` only; the console shows them only after capability is declared in the self-registered schema; the source object has
`additionalProperties:false`, and old firmware returns 400 for any new key):

| Field | Shape | Semantics |
|---|---|---|
| `url` | string, 8–1024 | Direct stream-acquisition address; scheme must match `transport` (`rtsp://` ↔ rtsp/rtsp-udp;
  `http(s)://` ↔ mpjpeg/jpeg), and a host is required; **embedded userinfo (user:pass@host) is forbidden**,
  and NE validation failure returns `config-invalid`. The address is stored by the platform, so prefer the first two modes when the camera supports ONVIF |
| `transport` | enum `rtsp`/`rtsp-udp`/`mpjpeg`/`jpeg` | The NI direct-source kind; selection determines the ffmpeg input template |
| `secret_name` | optional string, `^[A-Za-z0-9_.:,-]+$`, ≤128 | Points to a named secret **pre-provisioned by operations in the NI secret store**
  (username/password), which NI injects into the URL; NE does not create/copy the secret. Passwords never enter config or the NL database |

In direct mode, the virtual output subdevice's `local_id` is deterministically derived from the URL host, a short hash of the full URL,
the model id, and a short hash of the model version (`inference:url:<host>-<hash8>:<model-id>:<model-version-hash8>`). One URL can therefore
bind multiple model versions in parallel; rebinding the same URL+model id+version reuses the retained device and updates its connector.
Existing devices named before the version component was added are found through their source and `model_ref` and reused. The console suggests an editable
alias of "hostname · model-id@version detection" for a new output device; the alias is display metadata only, never participates in binding identity,
and is preserved on an exact rebind unless the operator edits it. Direct-source stream-start failure/401 is likewise reported by NI as `source-no-frame`;
NE/NI does not fall back to another acquisition mode or switch devices. `profile` is invalid in url mode (`config-invalid`).

- Cloud-side ONVIF modes reference only camera subdevices; stream URLs and credentials never remain in the cloud in ONVIF modes.
- When a stream is unavailable/has no frames, NI reports `source-no-frame`, carried to the cloud by connector status (see 15.6); NE MUST NOT silently fall back to snapshots.
- The console enables a selection only when the gateway's self-registered schema includes the corresponding mode in `source.properties.mode.enum`;
  the source object likewise has `additionalProperties:false`, and old firmware explicitly returns 400 for undeclared keys.

`trigger` (optional, default `event`) and rate parameters:

| trigger | Rate Field | NI Trigger | Semantics |
|---|---|---|---|
| `event` (default) | `max_idle_ms` (idle determination) | `command` | Event-driven: a synchronous read/diag to the virtual output subdevice triggers one inference (NI has no event-bus wake-up path in this slice) |
| `periodic` | `period_ms` (≥200ms) | `periodic` | Capture one frame and infer once per period |
| `continuous` | `fps` (0.1–60, default 5) | `continuous` | Continuous inference, capped at the FPS cadence (typical for stream mode; also valid for pulling snapshots from a snapshot source at FPS) |

`command` is an NI-side value and **is not** a valid cloud-side trigger; the cloud accepts only `event`/`periodic`/`continuous`,
translated by NE. The console displays continuous only when the edge schema's `trigger.enum` contains `continuous`.

`target_device` (optional string; omitted is equivalent to `"CPU"`, so old bindings without this field are fully backward compatible):

- An **operational decision at binding time**, describing "on which compute device results must be produced correctly"; it is not part of the model package. Hardware-specific
  artifacts are still distributed as independent objects according to the platform contract.
- Common values: `CPU` (default), `GPU`, `GPU.0`/`GPU.1`/… (manually enter indices for multiple iGPUs/discrete GPUs), `NPU`
  (may likewise carry an index), and `AUTO`; OVMS compound forms are passed through verbatim, such as `MULTI:GPU,CPU` and
  `HETERO:GPU,CPU`.
- Transport-safe validation (carried by the config JSON Schema self-registered in hello `connectors[]`, compiled/stored by NL and enforced on
  connector create/update, with matching upfront console validation):
  `{"type":"string","default":"CPU","minLength":1,"maxLength":64,
  "pattern":"^[A-Za-z0-9_.:,-]+$"}`; invalid values are rejected (`config-invalid`).
- Omitted means `CPU`: the console omits this field when the value is `CPU`, so CPU bindings on old firmware (whose schema does not yet declare this property and has
  `additionalProperties:false`) are unaffected; selecting a non-CPU value on old firmware is explicitly rejected when creating the binding
  (400), rather than ignored and silently run on CPU.
- **Hard-requirement semantics, no silent fallback**: the edge/NI MUST complete inference on the target device; if the target device does not exist,
  its driver is unavailable, or it cannot produce results, connector status MUST explicitly report `FAILED` + reason
  `target-device-unavailable` (see 15.6), and **MUST NOT** silently fall back to CPU and continue producing results.

- Status reports still use `v1/gateway/connectors/status` (`APPLIED`/`DEGRADED`/`FAILED` + reason),
  participating in existing connector reconciliation, drift advisories, and the manifest `connectors` section; do not configure `health_check`
  (a virtual device cannot support periodic resource-read), and the edge manages liveness according to `max_idle_ms`/`period_ms`/`fps`.
- **Phase A boundary**: at creation, the core does **not** intercept/validate `model_ref` (no inference semantics and no
  `if connector_type == "edge-inference"` special case). The console binding wizard performs the READY-inventory precondition check
  (only models that are `READY` and non-stale on this gateway may be selected); an instance referencing a pruned/unavailable model is reported by the edge through
  connector status as `FAILED` (reason `model-not-ready`). Cloud-side 409 `model-not-available`
  rejection and the generic `output_device` template (option B) are both deferred to later slices.
- The console option-A wizard sequentially calls two existing REST APIs within one user action: ① create a subdevice under this gateway referencing the
  `detection/v1` system profile; ② create an edge-inference connector with `device_id=<new-device-UUID>`.
  If step 2 fails, compensate by deleting the subdevice created in step 1.

### 15.4 `detection/v1` System Profile and Result Telemetry

Inference results are **ordinary telemetry** attributed to virtual output subdevice `device_id`; NL persistence/rules/alerting paths require no changes
(point carriers remain only `v_double`/`v_string`/`v_bool`). The platform includes a tenant-visible, non-editable, non-deletable
system profile `detection/v1` (migration 0086 seeds existing tenants, and tenant provisioning seeds new tenants;
deterministic UUID, idempotent). Phase A standard points:

| measurement_key | Carrier | read_write | Semantics |
|---|---|---|---|
| `detection_count` | v_double | R | Total number of objects detected in this frame |
| `top1_label` | v_string | R | Highest-scoring class (value = member of labels) |
| `top1_score` | v_double | R | Highest confidence score, 0–1 |
| `infer_latency_ms` | v_double (unit ms) | R | Server inference latency as an independent scalar suitable for trends/alerts |
| `detections_json` | v_string | R | Structured details, schema `nereid.detection/1` |

Per-class `<label>_count` points are optional and derived by the seed profile from model labels; **they are not seeded in this slice**.

`detections_json` (one frame per inference, boxes are not split across frames, and `max_detections` defaults to a limit of 100):

```json
{
  "schema": "nereid.detection/1",
  "model": {"id": "yiqisoft-yolov8n", "version": "1.0.0", "revision": "76937"},
  "frame": {"w": 1920, "h": 1080, "blob_key": "media/<tenant>/<device>/<uuid>"},
  "detections": [
    {"cls": 0, "label": "person", "score": 0.93, "box": [0.12, 0.08, 0.47, 0.91]}
  ]
}
```

- `box=[x1,y1,x2,y2]` is normalized to 0–1; evidence images are uploaded through the existing BlobRef mechanism in §10 and associated by
  `frame.blob_key`. **The NL rule engine does not parse `detections_json`**; alerts/aggregations subscribe only to scalar
  points, and details are for drill-down/archival only.
- "Capture one image and immediately view the result" uses existing `v1/gateway/command` (request-response
  read to the virtual subdevice), returns synchronously without persisting history, and adds no new frame type.

### 15.5 Three State Planes, shadow `inference` Block, and stale Watchdog

| State Plane | Channel | State Set |
|---|---|---|
| Model | manifest `models[].state` | EXTRACTING / VALIDATING / READY / FAILED / REMOVED |
| Runtime | top-level `inference` block in device-shadow reported (free-form JSON, no shadow schema change) | ONLINE / DEGRADED / OFFLINE / UNKNOWN |
| Binding | `v1/gateway/connectors/status` | APPLIED / DEGRADED / FAILED |

Shadow reported `inference` block shape (read-only consumption; NL does not write it back):

```json
"inference": {
  "state": "ONLINE", "endpoint": "http://127.0.0.1:8081", "protocol": "kserve",
  "models_ready": 3, "models_total": 4, "active_bindings": 2,
  "checked_at": "2026-10-25T08:00:00Z", "probe_interval_s": 30, "latency_ms": 12.4
}
```

NL stale watchdog (new NL responsibility introduced by this ADR, approximately 30s cycle):

- **Runtime plane**: evaluate only gateways with non-empty `agent_inference` and an existing shadow row. `state=OFFLINE` alarms immediately regardless
  of freshness; when `now - checked_at > 3 × probe_interval_s`, treat it as silent and alarm as UNKNOWN/stale;
  gateways with omitted `probe_interval_s` or that have never reported an `inference` block do not generate false alarms. Whole-machine death remains covered by
  heartbeat/LWT; the watchdog covers only "process alive but status loop silent".
- **Model plane (two stale-detection paths, rows not deleted)**:
  1. **Whole-frame lease**: reuse the `gw-manifest` lease; when the entire manifest stops and the lease expires, mark inventory stale
     (reason `manifest_lease_expired`).
  2. **Section-level silence (migration 0087)**: for gateways that have started reporting the `models` section, NL separately records its
     watermark `last_models_at`. If device/connector sections continue renewing the frame lease but the `models` section is omitted continuously for more than
     `15min` (approximately 3 full cycles), likewise mark inventory stale (reason `models_segment_stale`)
     and open the same per-gateway `GATEWAY_MODEL_STALE` alarm (both reasons share one dedupe key and are mutually exclusive).
     This specifically covers the failure shape "inference has been cleared, shadow shows 0/0, but the edge omits the section instead of sending explicit `[]`"—under the
     §15.2 contract, zero inventory is always correctly expressed as explicit `"models": []`, and omission is allowed only for read failure/not negotiated.
     A gateway that has never reported the section has no watermark row and is not falsely marked. The next successful reconciliation (including `[]`) automatically clears stale
     and the alarm.
- **Binding plane**: NL does not infer binding liveness itself (an event source may legitimately be idle) and only receives edge state; the edge uses spec
  `max_idle_ms` (event)/`period_ms` (periodic) to determine `idle-no-inference` (continuous
  produces inference persistently at FPS and is not idle during normal operation; its watchdog remains active, and stream-acquisition errors transition to FAILED after consecutive `source-no-frame` failures),
  consecutive failures reaching
  `error_threshold` are classified as runtime/source errors, and recovery immediately pushes APPLIED.

### 15.6 Unified reason Error-Code Table

The model section's `models[].reason` and connector `status`/`spec` failures share one transport-safe error-code table: **constant
identifiers, no vendor names, no path/IP/stack disclosure**, enabling alarm grouping and i18n display.

| reason | Applicable Plane | Meaning |
|---|---|---|
| `model-not-ready` | Binding | Referenced model is not READY (pruned / still EXTRACTING/VALIDATING / FAILED) |
| `model-not-available` | Binding | The `model_ref` does not exist on the gateway (cloud-side rejection reserved for a later slice) |
| `target-device-unavailable` | Binding | Required `target_device` does not exist/is unavailable (missing driver, device cannot be opened, etc.); the edge MUST NOT silently fall back to CPU (see 15.3) |
| `runtime-unreachable` | Binding/Runtime | Inference server unreachable |
| `runtime-error` | Binding/Runtime | Server returned an error |
| `inference-timeout` | Binding | Single inference timed out |
| `source-no-frame` | Binding | Source supplied no frame within the window |
| `preprocess-failed` | Binding | Frame acquisition/preprocessing failed |
| `postprocess-failed` | Binding | Result parsing/post-processing failed |
| `idle-no-inference` | Binding | No inference beyond `max_idle_ms` in event mode (DEGRADED, not a fault) |
| `resource-exhausted` | Binding/Runtime | Memory/GPU/handle or other resources exhausted |
| `config-invalid` | Model/Binding | Invalid configuration |
| `package-invalid` | Model | Invalid model package format (EXTRACTING/VALIDATING failed) |
| `checksum-mismatch` | Model | Model package checksum mismatch |

Unlisted custom values SHOULD use the same English `kebab-case` constant style; NL stores/displays them verbatim without enum rejection.

### 15.7 On-Demand Self-Diagnostics `inference.diag` (ADR-0035 operation)

The edge registers `inference.diag` v1 in hello `operations[]` (`interaction=request-response`).
It is carried by the existing operations invocation/result frames in §13, **with no new frame type**:

```json
// invoke params
{"model_ref": {"id": "yiqisoft-yolov8n", "version": "1.0.0"}, "source": "<optional-subdevice-UUID>"}
// result
{"reachable": true, "model_ready": true, "infer_ok": true,
 "latency_ms": 14.2, "frame_source": "snapshot_jpeg", "reason": ""}
// For a stream binding, frame_source is "rtsp" (actual acquisition type resolved by federation, without the address)
```

Used for one-click fault-domain isolation: whole-machine death (link health) / runtime down (`reachable=false`) / model problem
(`model_ready=false`) / source has no frames (`source-no-frame`).

The edge also registers read-only operation `camera.profiles` v1 (`interaction=request-response`,
risk=read, no step-up), allowing the console to enumerate available streams when binding a video stream:

```json
// invoke params
{"source": "<camera-subdevice-UUID>"}
// result
{"profiles": [
  {"token": "Profile_1", "name": "main", "encoding": "H264", "width": 1920, "height": 1080, "fps": 25},
  {"token": "Profile_2", "name": "sub",  "encoding": "H265", "width": 640,  "height": 480,  "fps": 15}
]}
```

NE resolves the subdevice UUID to an EdgeX device name and reads core-command `GetProfiles` (falling back to the simplified command name
`Profiles`), recursively parsing profile arrays in the response; results contain only token/name/encoding/resolution/frame rate,
with no URL, address, or vendor path; when the command is unavailable, return an error (the console allows manual token entry).

### 15.8 Alarms (Reuse ADR-0019 Pipeline)

Deduplicated and auto-recovering, one per object:

| Alarm Type | Severity | Dedupe Granularity | Clear Condition |
|---|---|---|---|
| `GATEWAY_MODEL_FAILED` | MAJOR | Per model `gateway:model:version` | Model leaves FAILED or is pruned |
| `GATEWAY_MODEL_STALE` | WARNING | Per gateway | Next successful models reconciliation |
| `GATEWAY_INFERENCE_RUNTIME` | OFFLINE→MAJOR; silence→WARNING | Per gateway | Fresh ONLINE/DEGRADED report |
| `GATEWAY_CONNECTOR_FAILED` | MAJOR | Per spec (existing) | Connector returns to APPLIED |
| `GATEWAY_CONNECTOR_DEGRADED` | WARNING (new generic type) | Per spec | Returns to APPLIED or transitions to FAILED (mutually exclusive with failed alarm) |

`GATEWAY_CONNECTOR_DEGRADED` is generic to **all** connector types (not special-cased for edge-inference), and
`idle-no-inference` is one of its trigger scenarios.

### 15.9 Console REST and WS

- `GET /v1/tenants/{tenant}/gateways/{gateway}/models`: returns the gateway model-inventory array, with elements containing
  `id/version/revision/task/family/backend/server_family/model_name/state/reason/labels/active_bindings/
  stale/stale_at/first_seen/updated_at`; empty inventory returns `[]` (never `null`). RBAC reuses
  `connector:read`.
- WS adds tenant-level resource type `model_inventory` (still one connection, server push), with NATS subject
  `nl.model.event.<tenant>` and frame `{kind, tenant_id, gateway_id}`, where `kind` is
  `inventory`/`stale`/`runtime`; upon receipt, clients refetch the gateway's model list/shadow rather than changing state from the frame.
- Binding creation adds no new REST: the wizard composes existing device creation (`POST .../devices`) and connector creation
  (`POST .../gateways/{gateway}/connectors`), with unchanged RBAC points for each.

### 15.10 Phase A Non-Goals

- No model-file upload/distribution, no ESS / object storage / OH integration, and no new MQTT topic (except `models` as
  a section of the existing manifest frame).
- No telemetry-ingestion path changes; no option-B `output_device` template or server-side `model_ref` 409 validation.
- No seeding of per-class `<label>_count` points; other task families add seeds and schema conventions in their respective versions.
